# Windows 看板架构原型：真实页面初筛

此为增量改造前的初筛记录；后续结果见[来源增量发布与业务视图复测](INCREMENTAL-REPORT.md)。

本文原型的“冷服务”测量从预建实验索引启动，未包括计时前的日志解析/入库/副本准备及运行中的真实来源检查和追赶；OS 文件缓存未清空。同一份事实和原网页资源不等于正式服务的完整启动工作相同。B0 另有导入模式限制，下文单列，不能据此认定正式项目完整冷启动只需数秒。

日期：2026-11-02。业务基线：v0.8.5，`6d458ca`。本阶段继续使用浏览器，Linux/macOS 后置；没有修改正式服务、活动库、`src/` 或 `public/`。

环境：Windows x64，Intel i7-14700KF，28 逻辑处理器，约 32 GiB 内存；Node 24.19.0，Rust/Cargo 1.98.1。四个原型共用同一 Chromium 和原页面资源。

## 判断

**当前没有满足“切换快、更新也快”的合格胜者。** 三个 Rust 原型的重复切换达到 200 ms 目标，但四个原型的 100 次版本更新全部超过 1 秒。浏览器已经能做到百毫秒级切换，本阶段继续保留网页形态。

Rust + SQLite 与 Rust + redb 的结果接近，DuckDB 的更新更慢。本轮没有证据支持为了这一负载直接替换 SQLite，也不能把完整发布路径的差异归因为语言本身。下一轮应先改“每次小变化仍重建全历史、重算业务视图”的数据流。

## 本阶段实际改动

四个后端提供按来源读取变化的 `/api/changes`。看板 gateway 首次读取事实，后续通过薄 `/api/status` 检查版本，仅变化时读取来源替换。无变化时不再搬运全量事件或完整 context。

普通日期范围的 totals、eventCount、sessionCount、homeCount 实际采用对应后端 `/api/query` 的结果。费用、额度、别名合并、分组与周期对比继续使用原产品业务公式，没有把基础聚合速度冒充完整业务速度。

共享视图按版本、完整筛选、价目和时钟边界缓存；滚动一天范围逐次计算。每个请求捕获自己的 revision/carrier，core 版本不一致最多重试三次，不能混合新旧汇总。冻结使用独立 view ID，绑定后端快照、asOf 和价目；同一事实版本两次暂停不会覆盖旧视图。

Node 旧快照缺少来源分组时，只有可证明的单来源非空情况才还原；其余返回明确的 409/reset-required。旧 report 保持兼容，没有把不可还原的历史当空数据返回。

## 测量边界

- 输入是相同的 159,610 条冻结真实事件，包含六种来源；fixture SHA-256 为 `f498f2bf26f7c31a528c0f63af9d47a25c1328a819e38d9c05ba420c32bc96b1`。
- 五组依次运行，每组独立数据库和回环端口；测量期间没有并行编译或其他验证负载。B0、Node 与三个 Rust 组分段执行，环境中断没有重测或丢弃 Node 已完成结果。
- 切换共 100 次，按今日、本周、本月、全部循环，各 25 次。先准备常用视图，因此这是重复切换的成绩。首次业务计算保留在原始记录，冷服务另测 3 次。
- 重载共 100 次：服务常驻，原页面重新加载。它与首次启动服务的冷加载分别统计。
- 更新共 100 次：每次替换一个单事件来源，token 总量比上次多 100 万。计时从写入隔离索引前开始，直到响应 revision 正确、页面指标 title 中的精确总数正确，并等待两个动画帧。没有用旧缓存或 DOM 手工改值完成检查。
- 更新数据由已验证事实直接进入索引，**不包含原始文件检测、读取、解析或浏览器自动检查间隔**。这是明确触发范围刷新后的更新路径；自然自动刷新另测。
- 固定输入基准使用同一 asOf。B0 通过子进程 Date 钩子固定时间，定时器与 performance 时钟保持真实；另外的浏览器检查使用默认真实时钟。
- p95 使用 nearest-rank，保留全部成功样本及慢样本；失败单列。3 次冷启动只报告观测范围，不作为稳定 p95。
- 服务进程树包含 gateway、后端及当时仍在运行的子进程，另统计 Chromium 进程树。内存是离散采样的 private bytes/working set，**不是峰值**；B0 未完成持续更新阶段，不能拿其空闲采样冒充完整资源优势。
- OS 文件缓存未清空；B0 沿用既有数据库布局，原型读取重建后的实验库。结果用于本机原型初筛，不能单独归因于语言或数据库品牌。

## B0 的范围和失败

B0 调用正式 `createUsageServer` 的 importContext 路径读取冻结索引副本，阻止真实来源发现及价目刷新。它保留默认 224 MiB 执行器堆限制，也没有启用普通运行模式的持久汇总缓存。原型 gateway 的堆上限为 2 GiB；这不是相同内存预算的比较。

B0 完成 3 次冷启动和 100 次切换：切换 p50 **291 ms**、p95 **591 ms**、最大 **1,767 ms**；76 次超过 200 ms。随后原页面重载返回 `EXECUTOR_EXITED`。Node fatal report 确认为 JavaScript heap out of memory，预跑和正式测量均复现。

因此 B0 的重载、更新和持续资源对照不完整，不能把失败记作零耗时，也不能宣称原型在这些场景胜出。这个故障属于本次隔离导入路径，不能直接推断用户日常运行模式也必然发生同样故障。本阶段没有调大 B0 堆来掩盖它。

## 结果

下列切换、重载、更新各 **100 次**，列出 p95；重载指服务已常驻。

- **P1 / Node + SQLite**：切换 **672 ms**；重载 **166 ms**；版本更新到指标显示 **2,638 ms**。更新最大 **7,054 ms**，没有丢弃该慢样本。
- **P2 / Rust + SQLite**：切换 **134 ms**；重载 **97 ms**；版本更新到指标显示 **3,212 ms**，最大 **4,384 ms**。
- **P3 / Rust + redb**：切换 **128 ms**；重载 **100 ms**；版本更新到指标显示 **3,097 ms**，最大 **4,394 ms**。
- **P4 / Rust + DuckDB**：切换 **171 ms**；重载 **181 ms**；版本更新到指标显示 **5,134 ms**，最大 **7,313 ms**。

P1 的 100 次切换有 30 次超过 200 ms；三个 Rust 组均为 0 次。四组更新均为 **100/100 次超过 1 秒**。P1 不是所有范围都慢：“全部”范围的 25 次切换 p95 为 698 ms，而“今日”和“本月”分别为 75、64 ms。B0 的“全部”范围 p95 为 174 ms，不能只用总分布掩盖这个局部退步。

冷服务启动到默认页面指标显示，各 3 次的观测范围：B0 **4.04–4.15 s**，P1 **2.88–3.20 s**，P2 **3.15–3.66 s**，P3 **3.15–3.59 s**，P4 **3.67–4.18 s**。这些次数不足以描述冷启动尾部。

每个原型采样 7 次的服务进程树私有内存范围：P1 **615–1,062 MiB**，P2 **1,639–2,404 MiB**，P3 **1,820–2,557 MiB**，P4 **1,776–2,626 MiB**。对应 Chromium 进程树约 **596–896 MiB**，不包含在服务数字里。内存占用是原型选择中的实际代价；这里没有用单个 Rust 进程的数字代替整个服务。

每组另观察约 10.5 秒空闲：服务进程树消耗 0.016–0.031 CPU 秒，Chromium 消耗 0.031–0.078 CPU 秒。采集器没有运行，这项短观察不能替代常驻长测。

## 耗时所在

100 次更新的**平均**分段如下，含服务端 Server-Timing 和客户端提交计时；剩余时间含 HTTP、浏览器处理与等待两帧。

- P1：提交 **47 ms**，feed **268 ms**，业务投影 **1,339 ms**，基础 core 查询 **561 ms**。
- P2：提交 **1,468 ms**，feed **191 ms**，业务投影 **1,259 ms**，基础 core 查询 **112 ms**。
- P3：提交 **1,383 ms**，feed **176 ms**，业务投影 **1,254 ms**，基础 core 查询 **118 ms**。
- P4：提交 **2,229 ms**，feed **182 ms**，业务投影 **1,368 ms**，基础 core 查询 **940 ms**。

四组各只有 **101 次 changes feed**：首轮完整载入，加 100 个变化版本；其余约 307–309 次薄版本探测总共约 **10.5 KiB**。这证明重复切换已经走新路径。不过变化版本仍携带完整 context，每组整个运行的 feed 累计 **2.51 GB**；重复元数据传输仍需改进。这个字节数来自后端到 gateway，不是浏览器的响应体大小。

静态路径解释与这些测量一致：Rust 存储提交返回完整 State，随后 `PublishedState::from_commit` 重建全部 prepared events；共享 Node 投影在数据变更后重新计算完整业务视图。这是下一阶段可直接修改并验证的路径，不是更换数据库后就会自动消失的工作。

## 正确性与自然刷新

- Node 后端 **23/23**、Rust release/all-features **28/28**、gateway **14/14** 测试通过，共 **65 项**。
- 四后端的小夹具六种筛选和真实 159,610 条事件的四范围完整业务投影对拍通过，包含费用、额度、周期对比和元数据。
- 两个并发请求跨提交时的版本一致性、同版本双冻结的独立时钟/价目、时钟边界和滚动范围均有回归检查。
- 原型百次更新中，每次都检查了响应修订与页面精确 token 数；这些检查不等于一小时或八小时耐久验证。

默认真实时钟下，四组原页面的暂停、冻结读取、恢复显示新修订以及无用户操作的自动刷新均通过。每组自然自动更新各观察一次，commit 到指标显示为 **59.98–60.00 秒**，包含原页面的 60 秒检查等待。这项小夹具并行检查用于功能验证，不是 p95 或架构排名。

所以，即使基础查询继续提速，自然刷新也会受检查周期限制。后续需要明确的版本通知机制，同时保留断线后的版本检查；当前没有改正式页面的刷新策略，也没有把手动点击成绩当自然刷新成绩。

## 后续实施边界

当前只完成真实规模的页面初筛，尚未完成 S4 的扩展规模、持续混合负载及完整故障矩阵；一小时/八小时长测、四种来源实时接入补全、生产迁移/备份接入仍未完成。Linux/macOS 按用户要求后置。没有合并、发布或替换正式服务。

产品 view 绑定和冻结 carrier 为实验进程内保留，尚无长期容量控制；后端持久快照与此不同。进入生产接入前需要补齐这部分验证和回收策略。

下一轮先固定现有事实与业务契约，验证“单个来源变化只更新该来源和受影响的业务视图”。范围查询应直接读取已发布业务视图。保留 Node + SQLite 控制组与 Rust + SQLite 对照，先消除全量重读、重建、重复元数据传输，再决定是否值得替换语言或存储；本轮没有扩展成新的第五、第六个原型。
