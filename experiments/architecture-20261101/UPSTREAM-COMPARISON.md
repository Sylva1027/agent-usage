# 上游与当前实现对照，以及完整重建的下一步

日期：2026-11-02。结论：**当前项目的功能、统计语义及历史管理更完整；上游已有合理的流式 SQLite 基础。现有证据不支持把当前性能问题全部归咎于上游，也没有证明两版在等价业务下谁更快。**

本轮完成源码比较、Git 追溯、两个合成行为对照及既有重建探针再分析。未修改正式源码、替换活动库或启动下一项性能改造。

## 已有基础与当前扩展

| 方面 | 上游共同祖先 | 当前项目 |
| --- | --- | --- |
| 存储与采集 | SQLite/WAL、预编译 INSERT、单文件事务与回滚、逐条流式解析、仅重建变化文件 | 保留基础，并扩展来源核验、跨文件基线、额度事实、修订与 rollup 等 |
| 来源 | Codex 各 home/渠道，及项目用量日志 | 再加入 DSH、ZCode、OpenCode、Claude Code、WorkBuddy，各自保留原格式语义 |
| 跨 rollout 累计 | 每个文件以零为累计起点 | 同 home/session 的跨文件前序基线，以及首请求累计修正 |
| 原始文件消失 | 从索引删除对应来源，外键级联删除事件 | 保留已入库历史，并区分 missing 与来源扫描失败 |
| 压缩与发布 | 普通 JSONL，变化文件按读取前 size/mtime 发布 | 增加压缩来源、多帧检查及部分来源提交前指纹复核 |
| 业务 | token、会话、渠道/模型/项目与周期比较 | 新增更细的 token 完整度、计价、额度窗口、历史纪录、仓库、多周期视图和冻结快照等 |
| 历史管理与重启复用 | 原始文件的派生索引 | 增加历史保留、备份/归档/恢复、冷历史读取、rollup 和持久摘要 |

上游的 `replaceFile()` 在 `BEGIN IMMEDIATE` 内删旧事件、流式插入并提交，异常时回滚；不是把全部事件读入内存后再统计的玩具实现。其 `sync()` 也已经按文件变化决定重建。[上游代码](https://github.com/DhWU-coder/codex-usage/blob/6bc2debeaf62ca03b6220d02e61d4b73d97dd7f3/src/usage-store.js#L153)

但它的“增量”仅到文件级：一个长文件追加后仍需重读该文件；每条事件仍有一次 SQLite 调用。当前也延续了这条通路，并增加更多列、索引、触发器及语义核验。上游路径较短、更容易审阅；当前覆盖更多真实问题，同时也承担更大的维护与运行成本。

当前的来源、统计及恢复实现程度明显更高；可静态确认或由本轮夹具证明的改进，不能外推成所有故障组合都已经可靠。价格是当前价目下的估算等现有产品语义，也不能被当作与上游 token 统计相同的工作。

## 两个实际运行的行为对照

入口：`upstream-comparison-check.mjs`。两版读取同一组人工构造的两份普通 Codex JSONL；同一 session，先累计 100，再累计 160，第二次请求增量为 60。使用各自独立数据库，完全不接触真实来源。

| 情况 | 上游结果 | 当前结果 | 解释 |
| --- | ---: | ---: | --- |
| 两个文件的历史 total | 260 | **160** | 上游第二文件从零算起，把160再记一次；当前使用前序基线 |
| 删除这两份原始文件，再同步 | 0 | **160** | 上游把索引当现存原始文件的镜像；当前承担持久历史保留契约 |

跨文件第一项是明确的统计改进。第二项需要区分目的：按原始文件镜像的旧产品约定，删除来源可以意味着删除统计；但对当前“历史不得因上游清理而丢失”的要求，上游不够用。上游没有把扫描失败和真缺失严格分开，静态路径还存在暂时发现失败后级联删除索引事实的风险；本轮没有制造真实权限故障来验证此分支。

## 性能欠账来自哪些演进

Git 的内容追溯给出了两个明确归属：

1. `29624998376bdd69852fb4ae7b9f40a0a1ca37ef`（2026-09-24）加入 `previousCumulativeForSession` 及跨文件累计 SQL。刚优化的复合索引正是服务于这条后续新增查询；上游没有该查询，不能把它缺少配套索引归为上游已有瓶颈。
2. `cfbb03258f892e19eecf96e3b1b0a4e87bd65724`（2026-09-26）加入 `recordsForRange` 历史纪录。今天页面因此需要历史范围的信息；后来虽做了连接级缓存，完整历史扫描与失效粒度仍有进一步优化空间。

这两项新工作有明确业务价值，但接入时也需要同步设计合适的查询、索引和可复用派生结果。当前重构应补齐这部分性能设计，保留语义改进。

## 继续优化完整重建：已定位的下一处工作

重新分析[索引接入后的完整重建](INDEX-STAGE-REPORT.md)探针，当前 53.629 秒中的实际观测如下：

| 项目 | 本次观测 | 口径 |
| --- | ---: | --- |
| 整个来源同步 | 50.555 s | 包含各来源解析、写库与其他同步工作 |
| JSON.parse | 1,432,363 次 / 10.167 s | 全执行器累计，包括不同调用位置；不是互斥阶段 |
| 事件 INSERT | 146,412 次 / 6.895 s | 含新增索引维护及触发器，SQL API 墙钟累计 |
| COMMIT | 1,970 次 / 1.686 s | 保留当前按文件事务和耐久设置 |
| 首尾窗口指纹 | 7,458 次 / 3.744 s | 必要防竞态检查与重复读取都在内，不能全部删除 |
| DSH 两次逐行流 | 161 个文件 / 322 次 | 首遍总3.936 s，第二遍总5.512 s；第二遍包含下游消费 |

这些是嵌套或局部累计，不能简单相加，也不能把生成器耗时全部当作解压 CPU。

`src/dsh-usage.js:384` 首遍完整解压、解析以取得头信息和全部 parser 告警；`:480` 再完整解压、解析以提取用量。代码和161组两遍调用的 trace 一致。这来自后续来源接入及降低全量对象占用的实现，不是上游通路。第一遍并非可直接删掉：它保留了完整校验、告警先于事件、版本判断及首个 session header 的现有约定。

**建议下一实施子阶段只推进一个候选：优化完整导入通路，先验证 DSH 可否一次解压/解析并使用有界暂存。** 保持公开 reader 的坏帧、坏行、版本、事件顺序和告警契约；不能退回全量解压字符串或完整 row 数组。必要暂存引入的内存或磁盘成本也计入。首遍3.936秒是观察到的工作量，不是保证可全部省掉的时间。

候选先以损坏帧、跨帧半行、晚到/重复 header、回调异常和大记录夹具对拍，再用同一份真实来源与原页面完整重建复测，同时记录处理字节、JSON次数、峰值内存及写入量。收益不足或资源退化就不接入。之后再按独立测量决定是否处理逐条 INSERT/异步回调，避免一次混改后无法归因。

历史纪录持久化仍是日常刷新与切换的主线；在本次重建中它约0.72秒，单独解决它不会让53秒级全量导入明显变快。增长基线和多冷分片验收仍按原计划保留；本轮未开始这些实施。
