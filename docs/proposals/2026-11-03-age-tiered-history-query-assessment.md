# 历史按年龄分层查询：评估与验证提案

日期：2026-11-03。状态：**仅评估，等待反馈**。本轮没有进入 B3/C，没有启用周/月投影、迁移或删减历史，没有启动容量基准或重启用户服务。

## 结论与建议

建议采用一个方向：**保留完整权威事实，复用并补齐可撤回的持久业务统计；普通历史图表可以按年龄默认显示自然周，三年前按月继续作为候选。** 首先解决主摘要失效后重复处理无关历史的问题，再验证是否值得额外保存周/月结果。不要先建一套与现有日级 rollup、纪录表重复的数据库。

年龄规则本身不能解决当前 B2 的慢刷新：只读检查确认，测试中的全部记录都在 2026 年 8–11 月，**一年前、三年前记录均为零**。现在为一年前的数据加规则，不会改变此次 10× 样本的处理范围。真正可能改善性能的是查询执行和失效方式发生变化，这也应当惠及一年以内的高密度数据。

不建议物理只留周/月总数。这样会损失现有精确日期、重计价、去重、日纪录及修订能力；它不是本轮已经获准的保留政策。这里的“完整权威事实”指现有规范化事件、额度观察、来源身份、修订关系、必要解释证据及冷包契约，不要求另行收集聊天正文。上游原文件已经消失、仅留在现存索引中的历史也必须保留。

## 1. 10× 到底增长了什么

依据：[数据生成器](../../experiments/architecture-20261101/growth-dataset.mjs)、[行格式生成器](../../experiments/architecture-20261101/growth-line-inputs.mjs)、[SQLite 格式生成器](../../experiments/architecture-20261101/growth-sqlite-inputs.mjs)及私有数据集 manifest。

- 初始 1× 为 **146,412** 个事件，10× 为 **1,464,120** 个事件；额度观察分别为 71,153、711,530 条。
- 两档都固定 **6 类/6 个来源实例、1,968 个来源文件、1,729 个会话**，同一来源布局及会话身份，增加行数、事件和输入字节。
- 合成时间范围固定为 **90 天**，起点 `2026-08-01T00:00:00Z`。manifest 的 `coldSegments` 为 0。
- 这证明的是同一时间跨度的**密度增长**，没有同时证明文件、会话、实例、冷分片或使用年限增长。

本轮通过 `new DatabaseSync(file, { readOnly: true })` 检查 B2 的隔离页面数据库和独立 oracle，没有调用会触发派生构建的 `UsageStore.open/sync/dashboard`。年龄比较使用固定 UTC 日期 2026-11-03，门槛分别为 `2025-11-03T00:00:00Z`、`2023-11-03T00:00:00Z`；只是计算年龄分布，没有过滤掉本日稍后追加的记录。

检查结果：

- 1× 页面库现有 **146,420** 事件：8 月 50,431，9 月 48,803，10 月 47,178，11 月追加 8；最早为 8 月 1 日，最晚为 11 月 3 日。一年前/三年前均为 **0**。
- 10× 页面库现有 **1,464,129** 事件：8 月 504,308，9 月 488,040，10 月 471,772，11 月追加 9；最早为 8 月 1 日，最晚为 11 月 3 日。一年前/三年前均为 **0**。
- 两档实际 `source_files` 都为 1,968，`DISTINCT session_id` 与 `(home_id, session_id)` 组合数恰好都为 1,729，冷分片都为 0。只有 1,684 个路径贡献了事件，不能把它当作发现文件数。
- 10× 独立全解析 oracle 的以上分布与页面库一致；此前 B2 已做完整事实多重集对拍，本轮没有重复执行该容量测试。

完整聚合证据与数据库位置保存在忽略目录 `output/architecture-20261103/age-tier-assessment/age-distribution.json`。里面没有导出事件正文。本轮统计是 **B2 追加之后**的快照，与 manifest 的初始计数分开使用。

B1 已有 365/730 天的事实库后派生诊断，但那不是 B2 的真实来源端到端样本，也没有覆盖三年门槛，不能代替本提案的年龄边界验证。

## 2. 当前时间、内存和 I/O 的证据

主要测量依据：[B2 原页面诊断](../../experiments/architecture-20261101/B2-PAGE-DIAGNOSTIC.md)、[B2 单源增长诊断](../../experiments/architecture-20261101/B2-GROWTH-DIAGNOSTIC.md)及 [B2 总报告](../../experiments/architecture-20261101/B2-REPORT.md)。以下数字是已有观察，不是本轮新基准。

### 2.1 已经测到的成本

- 10× 原页面普通追加到正确新值绘制：Codex **33.145–35.957 秒**，DSH **22.891–24.193 秒**；today/week/all 切换为 **30.222 / 7.926 / 20.912 秒**。这是少量诊断样本，不是 p95。
- 其中 today 请求范围自身只有 **3 个事件、3,000 token**，页面仍耗时 30.222 秒。这说明不能仅按所选范围的记录数解释整页工作；看板还伴随元数据、周期对比等计算，但它们各自的独占耗时仍待分段确认。
- 10× Codex 单次追加范围内，采样 CPU 为 **30.766–31.391 核秒**、逻辑读取 **13.278–14.632 GB**、逻辑写入 **1.261–1.279 GB**；DSH 相应为 **19.969–23.016 核秒**、**7.600–9.328 GB**、**1.006–1.027 GB**。GB 为十进制。这里有大量服务端工作，不能只从页面柱数解释延迟。
- 服务树采样 RSS 最高 **573.50 MiB**，发生在六次追加后、等待漏 SSE 的轮询恢复期间，尚未冻结。该样本中 gateway 约 **209.92 MiB**、executor 约 **334.72 MiB**，另有原生 helper 与 conhost；不能只优化执行器后便宣布整树达标。
- 10× 状态目录运行后为 **1,890,900,348 字节**。原采样器扫错目录，磁盘峰值尚未测得；不能把其 0 当作零磁盘成本。
- 1× 页面计时与完整回归重叠，不拿它和 10× 计算严格增长倍率。CPU/I/O 是采样窗口内服务树计数，读取/写入是 OS **逻辑传输量**，不是物理磁盘量、解析器输入量或某张表的专属成本。

### 2.2 从代码可以确认的工作

1. **显示已经粗化，计算未必粗化。** `public/timeline-utils.js` 的 `deriveTimelineBucket` 已按柱数上限在日、周、月间选择，周从周一开始。`src/usage-store.js` 的 `summarizeInReadTransactionCore` 在主投影 miss 时仍经 `timelineRange → costEventsForRange` 逐事件计价，并同时累计分组等结果。把 bucket 改成 week/month，不会自动绕过这个遍历。
2. **更新仍会失效较广的结果。** 主投影的事实键包含变化版本和上下文，`syncRound` 在派生数据变化后清除 `summaryProjectionCache` 等进程缓存；`UsageSummaryCache.readSourceState` 的持久摘要签名还包含来源指纹、价格、额度/证据及发布状态。B2 页面样本的相关摘要均为 miss。需要缩小失效范围，不能笼统地说“项目没有缓存”。
3. **存在受上限约束但仍较大的逐事件载体。** `HistoryQuoteInputs` 每行 86 字节，16,384 行一块，预算 128 MiB。若全部捕获约 146 万事件，单是分块缓冲约 **120.94 MiB**，还不含字符串等开销；超预算会弃用。它是内存调查的重点，不是已测得的本次实际驻留量，更不能直接归因为 573.50 MiB 的全部来源。
4. **额度、去重、纪录已有容量改造。** B1 已有磁盘额度窗口、精确成员、持久日/周/月纪录和 dirty-day rollup；时间线成员集合超小预算后会落临时 SQLite。不能把 B1 前的无限全量集合当作当前唯一瓶颈。新增投影应复用这些结构，检查剩余计价、分组、序列化和维护成本。
5. **进程内缓存生命周期很短。** `src/usage-executor.js` 仍在空闲 200 ms 后退出，进程内结果不保证跨请求保留；持久视图的复用不能依赖执行器常驻。

### 2.3 年龄/桶粒度不能消除的成本

- **来源可信检查。** B2 的 E: 页面样本没有可用 journal，采用 SHA 回退。单源 G1 中，约 2.02 GB 的 Codex 长文件追加需要两次旧前缀验证，读取约 **4.04 GB**，同步约 **3.15 秒**；活动 journal 下的同类单源同步为数十毫秒。G1 与 E1 是不同样本，不能用减法给页面剩余函数分配秒数。日志即使内容很旧，只要仍活动或可能修订，就不能因查询按周而跳过校验。
- **首次导入、确实受影响的重计价/证据修订、累计依赖修复。** 周/月视图不能让必要读取和解释凭空消失；必须单列其范围及成本。
- **多冷包完整性与权限。** `trySqlHistoryDashboard` 目前只支持特定单冷分片 all 快路；其他 `dashboardHistory` 路径仍可能请求 `completeHistory` 并合并事件。持久摘要发现冷分片时也有发布保护。本轮数据无冷分片，不能宣称年龄投影解决了 B3 的冷历史通路，或用它绕过 authority/校验。

**尚未定位到独占函数耗时。** 当前证据说明“来源证明成本 + 失效后较广的业务重算/物化”是必须分别处理的两类问题，但没有可相加的函数独占时间账本。无法声称某个函数占 80%、120 MiB 已被实际持有，或保证改成周桶后节省多少秒。

## 3. 三种方案的区别

### 方案一：只限制界面/API 最小粒度

一年前只允许周柱，三年前若批准则只允许月柱，但仍沿用当前查询计算。

收益限于可能减少返回槽位、绘制及部分桶状态；当前页面已经按范围自动选择周/月，额外收益可能很小。在现有 B2 数据上，年龄规则命中 0 条记录。不能预期它消除逐事件计价、来源 SHA 或全局失效，更不能据此承诺刷新/内存过门。

只要仍可读取事实，能力限制可撤销；但若同步禁止任意日期查询，则属于产品能力收缩，必须单独决定。**不推荐把它当作主要性能改造。**

### 方案二：保留事实，复用/补充周月查询投影

这是推荐路线。先让现有日级、成员和纪录结果覆盖主摘要实际需要的统计与失效，再按测量决定是否保存额外周/月结果。完整桶可读取已完成的贡献；边界及不支持的字段回到有界的细粒度事实。少量常见基础维度可组合，不预生成全部来源/过滤组合。

预期收益来自：未变历史不重新计价、重启能复用、成员去重不搬到 JS、查询只合并所需分区。它与“只对一年以前生效”是两件事，应首先在当前密集的 90 天样本上证明这些收益。

边界与上限：

- 单个标量系列从日改周，时间行数可由一年约 365 行变成约 53 行；这是行数示意，**不是整页快 7 倍**。真实周槽数取决于首尾日期。
- 成员关系、定价充分维度、仓库/模型数及明细仍可能很大；查询成本由所需投影、精确成员、边界事实和输出共同决定，不能承诺所有查询常数时间。
- 原事实保留时，新增投影可能**增加磁盘占用和写放大**；首次构建及全历史重计价仍有与影响量相关的成本。
- 周与自然月不是嵌套分区，不能整周相加当作精确自然月。优先复用日级基础值或独立维护必要月贡献。

### 方案三：物理只留周/月汇总

只有同时删除事实、相应细粒度成员/解释材料后才可能明显减少事实存储，但损失不可逆；“保留足够多的成员和价格输入”又会侵蚀节省。精确任意日期、重算历史价格、日纪录、跨桶去重和未知未来指标都不能由几列周期总数恢复。

现有保留契约及原文件已消失的事实，使它不能作为普通缓存清理处理。**本轮不建议采用，也未获实施授权。** 若以后讨论，必须先决定可永久丢失哪些能力，独立验证备份、恢复及导出；不能用一个“按周查询”开关隐含批准删除。

## 4. 推荐的时间与查询契约（提案，未启用）

### 日历与年龄

- 沿用现有自然周：**周一 00:00 至下周一 00:00**；自然月为月初至下月初。内部按半开区间 `[start, end)` 归属，现有 API 的毫秒闭区间在适配边界转换，不改旧结果口径。
- 保留 `utc/local` 选择。local 投影记录已解析的 IANA 时区身份及日历/时区规则版本；Windows 名称需有稳定映射，不能只记一个 UTC offset。切换时区或规则变化后按新身份重建，不能复用错误分桶。此项是设计要求，非本轮跨平台实现。
- 夏令时用日历运算，不能假定一天总是 24 小时、一周总是 168 小时。测试 23/25 小时日及跨年周；周键使用周一日期，避免把 ISO 周年与自然年混淆。
- 建议“超过一年”按请求时区的**当前日期零点减一个日历年**，不是 365×24 小时；三年同理。2 月 29 日回退到目标年 2 月末。每个请求固定一个 `asOf`，时间推进也是依赖输入。
- 一年前严格为 `timestamp < cutoff1`；恰好等于门槛仍属新档。只有**整个桶结束不晚于门槛**时才作为旧档完整桶使用。门槛穿过的一周/月留在细档或按精确边界拆分，不把尚新的几天顺带粗化。

例：2026-11-03 的一年前门槛是 2025-11-03 当地零点；这天是周一，可以直接形成完整周边界。换成周中门槛，跨门槛周必须保留细分处理。年龄改变只改变路由资格，不需要每天搬移或删除事实。

### 任意起止、部分桶与跨档

建议首先把“一年前按周”限定为**普通时间线默认/最细展示档**，保留精确日期范围总计、导出和纠错能力。若要把 API 起止也强制对齐周/月，应另行批准能力变更。

对于保留的精确查询：

1. 将原请求范围按年龄门槛切为不重叠片段，并在同一发布版本下读取。
2. 每个片段的完整桶使用有效投影；不足整周/月的头尾、跨年龄门槛和不支持的字段读取细粒度事实或已有更细投影。
3. 头尾桶数虽有限，边界内可能有大量记录；必须流式/索引化处理，不把“只有两个边界”误当作成本恒定。
4. 范围仍是用户实际请求的范围，不能静默扩到周/月边界。比如只查周三至周五，不能返回整周总数，也不能按 3/7 分摊成“精确值”。

跨档图表建议继续返回单一展示粒度，取符合整段限制及现有柱数规则的较粗一档；近期部分在本次展示中合并。首尾柱只计请求范围内的事实，边界信息随现有范围数据表达。统计范围与图表粒度分开，不增加常驻技术提示框。若以后改为混合粒度图，需另评估 API/交互，不纳入首个切片。

三年前月档若启用，同样按完整自然月与部分边界处理；不能把跨月周整体分配到一侧。**本提案没有批准三年政策，也没有默认开启它。**

## 5. 哪些指标可以保持精确

- **Token、事件数和字段已知性：**可按充分维度合并，但保留 detail mask、未知值、不一致标记和 reconciliation。未知不能变成已知零。整数须保持现有安全范围与精度。
- **金额：**先按原请求语义计算可撤回贡献，保留分档、上下文、服务层级、缓存写入、时段、价格及证据版本。只有周期总 token 不足以重计价。价格/证据变化可能要求扫描全部受影响事实；汇率展示能否仅转换也以现有契约为准。浮点累加顺序/舍入可能因合并变化，必须与现有数值契约对拍，不能擅自放宽误差。不能据此预先宣称任意周/月合并均逐位相同。
- **比例、平均值：**保留分子分母及样本条件后重算，不平均多个平均值，也不按桶时长比例分摊金额/用量。
- **精确会话/模型/路径去重：**保留成员关系或等价精确查询，桶内数量不能相加成跨桶数量。当前总会话口径含 `COUNT(DISTINCT session_id)`，某些分组按 home 分开；不能趁投影迁移统一改成另一套组合身份。当前样本两种计数恰好相等不构成语义证明。
- **纪录：**最高日无法由周总数恢复。保留现有日/周/月纪录基础值、精确成员、并列规则；跨来源合并要重新比较周期值，不能只比较各来源自己的冠军。历史下降修订需要撤回旧贡献并重选。
- **额度：**滚动窗口、重置时刻、观测冲突、迟到快照及旧时刻冻结读取与自然周/月不同。继续走 B1 的窗口/原始观察通路，不能按事件年龄剪掉用于推断的旧观察。官方额度与证据 JSON 独立增长仍须验证。
- **TPS、TTFT、延迟、分位数：**当前运行版已移除 TPS，事件 schema/类型没有完整接收时间或生成耗时字段，不能拿 usage 的 timestamp 推导这些值。未来若恢复，须保留其独立有效样本与定义；周期平均不能恢复 p95，token 总数除以自然周时长也不是生成速度。保留现有事实不等于保留了从未采集的计时。

## 6. 修订、恢复、发布与空间

这里复用主计划已有事务、dirty partitions、持久进度和发布版本，不新建通用调度框架。

- **修订可撤回：**保存能定位贡献的来源/事实身份。替换、删除或旧行修订先撤回相应周期及成员贡献，再加入新解释；成员可能被多条事实支撑，不能删除一条就把成员从桶中无条件删除。不能只支持正向相加。
- **累计依赖不按年龄截断：**旧文件修订可能影响同一会话后面的文件。继续使用 B2 的持久修复队列与发布阻塞；未修复的上下游不能混合成完成版本。原文件缺失但有留存事实时，保留历史；解释依赖不再可恢复时沿用明确失败语义，不能假定差值为零。
- **构建可恢复：**从现有权威事实构建，不以空库重抓来源代替迁移。按有界字节/行批次写候选结果与游标；源版本改变时记录待追赶分区，完成核验后切换发布指针。SIGKILL、磁盘满、事务回滚后恢复，不把半成品当作完整首屏。
- **一致版本：**summary、timeline、metadata、额度、周期对比、成员页绑定同一事实边界、价格、证据、时区和算法版本；固定请求时刻。不能拼接旧周表与新事实来“快速刷新”。只有旧完整版本可读也不算新数据完成。
- **跨库/WAL：**派生库与事实库的两个提交不天然一起原子。沿用版本核验和可重建缓存边界，短事务分批推进；不以贯穿重建的长读事务无限钉住 WAL。若无法获得一致候选就重试或保留旧发布，不发布混合状态。
- **回退：**缺失或失效投影可由事实有界重建，回退须计时并记录原因。不能回到会 OOM 的全量 JS 事件数组，也不能绕过冷包完整性检查。频繁触发全历史回退就是性能失败，不能只测命中路径。
- **空间：**同时核算事实、成员索引、日/周/月贡献、候选与已发布双份、临时 SQLite、WAL/SHM、备份及中断残留。只保留必要候选，按已确认发布边界回收可重建数据；不得回收唯一权威历史。细粒度日表不能因周表存在而默认删除。

## 7. 后续验证：只提出，不在本轮执行

以下为**同一候选的三个验证步骤**，不是重新启动多路线原型，也不自动进入 B3/C。

### 步骤一：补齐可归因的测量

复用 B2 1×/10×、原页面、默认堆和源校验规则。给来源发现/证明、事实提交及依赖修复、派生维护、摘要/纪录/额度、执行器启动、序列化/IPC、通知/API/绘制增加轻量边界。嵌套调用用独占与包含时长区分，重型内存分析单独运行。

记录每阶段实际访问事件、命中/失效分区、价格调用、证明字节、临时成员/报价缓存高水位、返回字节；结合堆/外部缓冲/SQLite/网关 RSS 排查，不能用缓冲理论大小代替驻留测量。CPU、逻辑 I/O 分段采样注明误差，不能把重叠区间相加或用总 I/O 推导物理磁盘量。修正状态目录采样，获得真实派生/临时/WAL 峰值。

出口是一份可以解释当前 33–36 秒和 573.5 MiB 的分段账本，以及主摘要中一个范围明确的复用切片；不先承诺哪张新周表能节省多少。

### 步骤二：一个最小投影切片，与原语义对拍

若获授权，从最耗时且失效过宽的主摘要字段入手，复用日级/成员/纪录设施。验证普通追加只更新新增及实际依赖，先在 **没有一年旧数据**的原 B2 样本上证明收益。只有测量表明逐日合并本身仍是主要成本，再增加必要周投影；月投影需三年政策另行决定，不同时展开三套存储路线。

独立手算及小数据原算法对拍覆盖：非线性计价/未知字段、跨桶会话、跨 home 同 session、合并来源冠军、并列与下降、旧来源修订、重计价/证据变更、午夜/周月边界、SIGKILL/磁盘满、读取中发布。已有 63,752 个数字字段对拍是可复用回归，不替代新边界夹具。结果错误、历史丢失或混合版本直接失败，不能用快来抵消。

### 步骤三：把密度、年龄、文件和会话分开验证

主诊断采用 **4 个数据形状 × 2 个实现状态（当前 B2/候选）= 8 个对照单元**，其中每个单元分别运行来源追加与页面切换：

1. 原 1×，约 90 天，保持原文件/会话/实例。
2. 原 10×，仍约 90 天，只增加密度；年龄规则仍不命中。
3. 固定 10× 总事件量、文件/会话/实例，重新分布到约 **400 天**，明确覆盖一周年门槛前后；它是年龄/分区诊断，不代表按真实使用率生成的一年容量。
4. 固定同样总量与身份，分布到约 **1,200 天**，覆盖三周年门槛；月档仅作隔离候选对照，不能借测试启用产品政策。

每个形状都注入相同大小的近期追加、旧桶修订，并查询 today/week/all、旧完整周、任意头尾日期和跨档范围。固定输出/工作集的增长对照与输出本身增长的 all 查询分开报告。活跃 journal 与 SHA 回退作为独立环境层分别报告，不能互相代替。

另用小而可手算的独立边界夹具覆盖：门槛精确时刻 ±1 ms、周中门槛、跨月周、闰日、DST、UTC/local、跨年周，以及完全无旧数据的规则空操作。原样本没有冷包；后续冷包资格仍需 B3 单独授权和验证，不并入本次热历史收益。

固定总量的时间重排只能隔离年龄策略。真正一年/三年容量，还需按冻结来源画像增加总事件、物理文件、独立会话和输入字节，保留跨文件依赖，并记录联动轴；不能用移动日期替代这项验收。优先复用 B1 的会话/年份工具与 B2 输入格式，不在评估轮生成大数据。文件/会话独立增长和真实长期来源端到端验收仍是主计划后续缺口。

### 建议的通过门槛

沿用[主计划联合目标](../plans/2026-11-02-multi-harness-history-refactor.md)，以下都**尚未取得**：

- 正确性：既有保留历史、事实多重集、统计字段、舍入/未知性、过滤/去重、修订、窗口、恢复与发布契约通过。精确日期查询不出现静默扩大或比例分摊。
- 延迟：无变化、已有发布的完整进程冷启动 ≤2 秒；普通切换 p95 ≤200 ms；普通完整记录落地到正确新值绘制 p95 ≤1 秒。首次导入、OS 冷缓存、漏通知恢复和修订另报，不能混成命中成绩。
- 资源：默认堆不提高，服务树空闲连续 60 秒 ≤256 MiB、活动峰值 ≤512 MiB，浏览器单列；固定增量与输出时，10× 对 1× 的 p95 ≤1.3 倍、内存峰值 ≤1.2 倍。窗口覆盖后台追赶及必要整理，不能提前结束采样。
- 工作量：建议给**固定工作集的派生/查询阶段**增加 CPU 核秒、实测逻辑读写各 ≤1.3 倍的增长门；此为新提议，不是已有达标结果。来源证明须独立计量，但整页总时间/CPU/I/O 仍全额报告。SHA 场景必要前缀验证随长文件增长，若整页因此超一秒仍判该场景未达，不通过“扣掉校验”过门。
- 初建/重计价：允许随真实受影响输入增长；按记录/解码字节报告单位 CPU、I/O、耗时与临时空间。1× 同口径耗时或 CPU 回退超过 10% 必须复核；已有投影却仍反复扫描不相关完整历史判失败。
- 空间/维护：候选开发前冻结磁盘余量与写放大预算，至少容纳保留事实、已发布与一个候选及实测临时高水位；磁盘满也必须安全退出并可恢复。预算未填实或峰值未测，不能把容量门标为通过。无实测收益的重复投影不保留；不能靠无限双份、WAL 或积压换速度。
- 样本：探索性每格先少量诊断；正式声明 p95 前，每个追加/切换类别至少 100 次尝试、跨至少 3 个独立进程；各规模/实现冷启动至少 20 次。失败/超时不从分母移除，不用成功重跑覆盖。追加按独立节奏注入，报告队列最老年龄和停止负载后的追赶时间。

## 8. 需要决定的产品边界与下一步建议

建议先接受“保留事实、先复用现有业务统计”的方向，并把下一次实施限制为**测量账本 + 一个主摘要复用切片**；做完再决定是否增加周投影，避免先限制功能后仍然很慢。

在启用年龄政策前需要确定：

1. 一年前的周限制只管普通图表，还是也禁止精确日期/API/明细？本提案推荐前者，精确总计与导出保留。
2. “一年”是否采用上述当地日历周年与完整桶资格规则？UTC/local 切换是否继续保持现有能力？
3. 三年前月档是否确实需要？它仍是候选，本轮不替用户作批准。
4. 新投影实测能省多少工作、增加多少磁盘/写入？测量后冻结实际预算，不能先宣称免费。

可合理预期的是减少未变历史的重复处理、缩小查询工作集并跨重启复用。**尚不能量化节省秒数、RSS 或总磁盘，更不能承诺仅按年龄改粒度就使 B2 过门。**

本轮仅新增此提案及忽略目录内的年龄聚合证据；未修改生产实现。容量基准、周/月功能、迁移、真实一年/三年端到端可用性和多冷分片性能均未在本轮执行或证明。完成本次评估后停止，等待反馈。
