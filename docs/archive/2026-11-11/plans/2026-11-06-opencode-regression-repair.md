## 第一步：先做 OpenCode 的分段归因，再允许改代码

先冻结三份代码：退化前 `56e5805`、当前 `799d83e`、后续基于 `799d83e` 的候选。复用同一原始捕获副本和共同索引，不空库重建。固定价格检查的 1.1 秒无价格变化返回，真实价格变化仍另作正确性验证。

**首批仅 2 组：OpenCode 的 `56e5805` 与 `799d83e` 各 1 组。** 同一原页面按既有流程完成首次打开、两次追加、一次修订、today／week／all 切换和服务重开，保留真实来源检查、解析、同步、通知与新值绘制。

采用退出时落盘的有界分段记录，复用已有浏览器时序和工作量计数；仅对以下缺口增加记录，不对每条历史事件打日志：

1. 主进程请求接收、执行器启动／打开、消息排队、实际方法执行、返回、序列化、浏览器响应／绘制。
2. 来源发现／指纹核对、解析、事实发布、替换历史留存、派生维护、提交／checkpoint、SSE。
3. all／today／week 的额度、纪录、主摘要、元数据、周期对比的准备与读取；缓存命中／拒绝原因及相应事实修订、价格版本，不把首次访问新范围的正常 miss 当作缺陷。
4. 启动期间的源文件替换次数、事实变更次数、派生构建次数、读取／计价事件数、WAL／状态文件增长；区分旧索引价格版本纠正和纠正后的服务重开，两项都计时。

每项退化形成同一张“总增加 → 所属阶段 → 工作量是否增加 → 有效／重复工作 → 触发条件”账本；明确剩余未解释时间和记录开销，不重复累加嵌套耗时。

**有界追加规则：** 第一对仍无法复现或解释时，只再做一对反序 OpenCode 组，总计最多 4 组。Claude 先利用旧记录与共享慢段归因；仅在其问题仍独立存在时再做旧／新各 1 组，定位组总数最多 **6**。观察 CPU／I/O／进程等待与运行顺序影响，不能把同工作量的单次变慢直接认定为算法退化。

**进入修复的条件：** 至少明确一个额外等待／重复工作的触发机制，并建立小型确定性反例。预算耗尽仍未得到机制时，交付诊断账本并停止，不盲改生产代码或扩展整套矩阵；单次未复现不能把旧失败改为通过。

## 第二步：只修证据命中的共享慢段

按第一步结果选择实际需要的最小修改，不把下列方向全部实施：

| 若证据命中 | 具体修复方向 | 必须保留 |
| --- | --- | --- |
| 一次采集／查询中重复准备相同修订的视图，或先建旧目录视图再建新目录视图 | 在同一事实修订和本请求价格目录下完成一次必要准备，复用既有持久视图／已完成凭据 | 原子发布、真实价格变化失效、旧历史修订可回退 |
| 相同来源版本被当前请求重复检查／重复同步 | 复用既有完成凭据消除已证实的重复；外部写入或凭据失效仍核验 | 来源变更检测、外部任意表提交检测、正确新值提交后才完成刷新 |
| 排队、空闲退出／重启或同一执行器生命周期造成额外等待 | 修正命中的请求边界或调度；沿用已有活动请求持有机制 | 不增加常驻堆／进程，不单靠延长空闲存活时间追分，不阻塞关闭／恢复 |
| 价格目录重复拷贝／处理成为可测主要成本 | 在既有请求边界消除同一快照的重复处理 | 发起时捕获目录、同步全过程隔离、并发查询各用其目录 |
| 单个实际 SQL／派生读取退化 | 依据实际执行计划、读行数和调用次数修该处查询或复用路径 | 精确计价／顺序／成员去重、任意范围和修订语义 |

如果只是必须完成的一次旧索引版本纠正，正确列出其启动／留存代价；只能消除重复执行和不必要的派生重建，不能删除已留存历史或把必要工作藏到“已完成刷新”之后。WAL／状态增长要至少明确主要写入来源及是否重复，不以“没有新表”代替资源验收。

每个实际修复都先有失败反例，再验证修复后通过。复用已有价格目录并发、前缀保护、外部提交、晚到写入、修订／删除／回滚／重启测试，新增测试只覆盖本次新机制。主代理负责共享实现与原页面验证；如需委派，仅 1 名 pinned worker 独立负责确定性回归及逐值对拍，显式 `group/deepseek`／`max`／`fork_context:false`，文件单写、逐卡验收，不生成后代。

## 第三步：固定 8 组验收，防止把慢版本当新标准

修复及局部验证稳定后，仅一次 **4 来源 × 对照／候选 = 8 组**，包含 16 追加、8 修订、8 重开、4 对首次服务打开、12 对范围切换。候选全部基于 `799d83e`；各来源对照版本明确固定：

| 来源 | 对照版本 | 选择目的 |
| --- | --- | --- |
| OpenCode | `56e5805` | 恢复退化前的启动、刷新、修订和切换速度，不能只比已经变慢的 `799d83e` |
| Claude Code | `56e5805` | 收回后续追加退化 |
| ZCode | `799d83e` | 保住当前首次追加收益，而不是仅好于原来约 3.9 秒的慢版本 |
| WorkBuddy | `799d83e` | 确认共享修复未损伤已交付路径 |

全部使用同一份原始捕获、相同源变更计划、价格目录和堆预算，各组恢复输入与索引，交替运行顺序。记录并固定本轮 Node、浏览器、助手及盘卷环境；若与旧报告不同，必须单列，不能直接拼接历史秒数作为验收。不同对照版本逐行标注，不混成一个总体提速比例；旧版本有价格目录缺陷，业务／金额还须按同一权威目录独立验算，不能把旧错误的目录标签当作真值。

| 验收项 | 标准 |
| --- | --- |
| 延迟 | 首次打开、首／次追加、修订、重开及切换均不得同时慢 >10% 且增加 >100 ms；6 项旧退化分别判定 |
| 防止成本转移 | 同时比较首次服务打开、每次正确新值绘制、更新后服务重开；不能只展示刷新更快 |
| ZCode 收益 | 适用的两次普通追加各仅写 1 条，保留旧 ID／顺序，延迟对比当前 `799d83e` 过门 |
| 工作量与正确性 | 候选每次来源变更 1 轮同步，无空同步；保留真实变化的必要回退；响应、金额与计数严格逐值核对 |
| 资源 | 服务树 ≤512 MiB，gateway 512／executor 224 MiB + semi-space 4 MiB 不增加；CPU、I/O、WAL、状态增长单列，浏览器另列 |
| 回归 | 相关回归、必要完整检查、typecheck／lint；既有 4 项全套失败逐项保留分类，元数据文件启动失败继续定向核查，不能无解释归入旧失败 |
| 报告 | 全部有效样本和失败保留，每格一次、不声明 p95；不因未过门追加样本覆盖结果 |

**性能组预算：定位 2–6 组，最终验收 8 组，总计最多 14 组。** 未达到修复进入条件则不启动最终 8 组。只用当前实际数据，不扩展 1×／10×、完整重建、年份、冷分片或跨平台矩阵。

实施后交付一份集中对照表：对照版本、标准、候选结果、是否通过、未解释成本；本地提交后停止等反馈。失败仍记失败，不自动扩展下一卡或部署。计划阶段没有运行新性能组，也没有改动在用来源、索引、服务或助手。
