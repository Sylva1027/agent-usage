# 正式完整冷启动：分段实测与四原型同口径对照

> 历史材料，2026-11-11 归档。本文命令与状态属于原记录日期；源码及恢复方法见[归档入口](../README.md)。

2026-11-02，Windows。正式基线 v0.8.5，提交 `6d458caac0f3c7634321462f6b5345260faf3bab`。

## 结论

**目前不应继续以“更换语言和数据库”为主线推进 refact；应保留 Node + SQLite，优先修正查询、增量发布和持久业务视图。** 现有技术栈还有已经实测出来的改进空间，不能认定已经到达性能上限。

三个结果最能说明问题：

1. 来源无变化、持久缓存可复用时，正式版完整进程冷启动约 **1.29 秒**，四原型约 **4.77–5.68 秒**。关闭观测 hooks 的正式对照为 **0.93 秒**。
2. 同一份真实输入有 13 个文件需要同步、解析时，正式版为 **5.46–5.83 秒**，四原型为 **9.24–11.60 秒**。它们都执行了正式来源 gate，没有省掉采集工作。
3. 空索引完整重建约 **80 秒**。进一步定位到一类累计查询独占约 **29.6 秒**；仅在实验副本增加复合索引，相同探针下首屏从 **82.57 秒降至 52.03 秒**，减少 **37.0%**。全部用量事实与额度观测的字段哈希一致。

因此，先前原型的“三秒”不能用来证明需要换技术栈，也不能用来证明重构没有意义。它测的是预建静态索引之后的读取和计算；正式启动还要承担检查、追赶、解析，以及缓存失效后的业务计算。

## 测量边界与输入

计时从启动正式 CLI 的 `gateway` 进程之前开始，包含子服务启动、模块加载、价格配置加载、来源发现、来源指纹、缓存判断、必要同步/解析、证据读取、索引维护、业务计算、IPC/HTTP，以及原网页精确 token 指标显示后两帧。

Chromium 事先启动；每轮使用新浏览器 context。指标必须等于该轮 API 返回的精确整数，不能用圆整后的百万单位或显示旧值代替。这里测的是**进程冷启动**，没有清除操作系统文件缓存。

真实输入包括 Codex、DSH、ZCode、OpenCode、Claude Code、WorkBuddy。捕获清单有 **1,968 个用量文件，3,990,761,669 字节**；加上实际读取的辅助文件，共 **1,973 个文件，约 4.07 GB**。SQLite 来源采用只读在线 backup，包含已提交 WAL；两份复制期间变化的日志已经重新捕获并确认稳定。

已有索引包含 **1,975 个来源记录、160,862 条事件**，其中包括当前原始文件已缺失但仍应保留的历史。空索引重建得到 **146,412 条事件**。两种初始状态分开统计，不能用删除索引重建代替可靠的数据迁移。

测量分两层：

- **真实路径校准**直接读取正在使用的真实来源，正常执行真实目录/stat、指纹、同步、解析，只有状态写入被重定向到私有副本。早期正式版无探针一轮为 4.26 秒；最后一轮正式版为 9.32 秒，四原型为 13.64–14.46 秒。活动日志持续增长，各轮实际总数不同，这组用于校准完整路径，不用于严格相同数据的排名。
- **固定输入对照**对正式版和四原型提供相同的原始字节、来源身份和初始索引状态，仍由正式代码执行来源 gate。目录/stat 使用冻结记录；首尾指纹、内容解析与 SQLite 读取实际访问捕获文件。因此这组用于可重复的相对比较，不冒充真实磁盘元数据访问的绝对耗时。仓库路径 realpath 等环境查询保留实际只读访问。

没有使用 `importContext`、固定业务时钟或初始化 `skipCheck` 来跳过正式来源处理。价格自动刷新和来源发现调度保留。原型在同一个正式 gate 完成后，再核查并发布来源事实到候选内核；这部分适配成本也计时。

正式网关维持默认 `--max-old-space-size=512`，正式执行器维持默认 224 MiB old space、4 MiB semi space。原型查询 Node 内核使用 512 MiB old space，网关仍为 512；原生内核没有人为设置同等总内存限制，所以同时报告实际进程树资源，不能称为相同总内存预算。

## 同口径首屏结果

每格为 **3 次独立进程启动的中位数（最小–最大）**，单位秒；样本不足以报告 p95。每次都从相同初始状态的新副本开始。

| 实现 | 来源无变化，缓存可复用 | 13 文件需要同步、解析 |
| --- | ---: | ---: |
| 正式 Node + SQLite | **1.291（1.290–1.324）** | **5.563（5.461–5.834）** |
| P1 Node + SQLite | 4.983（4.772–4.999） | 9.483（9.240–10.872） |
| P2 Rust + SQLite | 5.265（5.204–5.342） | 11.018（10.125–11.301） |
| P3 Rust + redb | 5.240（5.174–5.429） | 11.430（10.956–11.598） |
| P4 Rust + DuckDB | 5.286（5.272–5.682） | 11.257（10.774–11.496） |

30 次标准启动全部完成。无变化的正式 trace 仍执行了一次 `readSourceState`，约 40 ms，之后恢复持久状态、命中摘要缓存；`sync` 和 parser 为零是检查后的正确分支。它不等于绕过来源检查。

本轮 12 项实验回归测试全部通过；最终独立核查确认 30 次标准响应成功、360 项业务对拍通过、87 个正式文件哈希未变，活动库中不存在实验复合索引。测试服务与两个 worker 均已退出。

四原型的两种初始状态共 **8 组对拍**，每组对默认页面及 all/today/week/month 检查 token、事件/会话/home 数、金额、渠道、模型、时间线、同比摘要，共 45 项，全部通过。整数精确相等，浮点金额允许 `1e-8` 误差；时钟派生均值使用正式共享函数统一 asOf 后比较。各轮页面均等待精确值及两帧，没有 pageerror。

这些候选共用正式的六来源采集/同步代码，替换的是事实存储与查询输出部分；它们还额外保留了一份正式索引。**这不是四种语言分别重写六类 parser 后的全栈成绩，不能把适配开销解释成 Rust/redb/DuckDB 的固有限制。** 但它足以说明当前四个原型都没有达到可替换正式路径的条件。

## 正式启动时间花在哪里

代表性分段来自 `formal-pending-sql`，完整首屏 **5.389 秒**：

| 阶段 | 实测 | 含义 |
| --- | ---: | --- |
| CLI 启动至服务登记 | 0.825 s | 包含实验加载 hooks，不能当正式模块本身的纯耗时 |
| `loadUsageStore` | 2.617 s | 来源检查、执行器交接、同步、状态发布 |
| 其中 `UsageStore.sync` | 2.000 s | 下面的来源处理属于此项内部，不能再次相加 |
| 文件首尾指纹探测累计 | 0.770 s | 实际读取文件首尾窗口，不是每轮完整读取 4 GB |
| 13 文件 `replaceFile` 累计 | 0.676 s | 含流读取、解析、消费写入与复核 |
| 服务层级及 quota 证据读取 | 0.182 s | 同步内部工作 |
| 已发布元数据计算 | 0.194 s | 与执行器状态交接有关 |
| 首次看板计算 | 1.428 s | 摘要、纪录、时间线和多周期比较 |
| 索引首次 `open` | 0.014 s | SQLite 打开本身不是主要等待 |
| 价格文件加载 | 0.016 s | 本轮读取已有配置；后台刷新照常运行 |

父子阶段是嵌套关系。启动、网页加载、HTTP/IPC、缓存发布和浏览器显示构成剩余时间，不能把表中所有数字简单相加。

额外业务细分轮 `formal-business-detail` 首屏 7.710 秒，其中来源 gate 4.190 秒、看板计算 2.141 秒。看板中的 **`buildRecordChampions` 单次耗时 1.250 秒**，today 时间线只有 0.095 秒。原因是 today 页面还要生成“历史纪录”信息，代码会遍历完整历史、逐条计价、累计日/周/月再选纪录。**页面选择“今天”，并不代表只处理今天的数据。** 仓库多周期比较另有约 0.296 秒。

这一段具体应重构的是历史纪录和多周期视图的生成与失效方式，而不是把 today 的总数查询换一种语言再实现一遍。

## 空索引完整解析，以及一个实际验证的改进

正式空索引首屏：无探针 **79.566 秒**；粗 SQL/阶段探针 **81.129 秒**；增加 JSON/SQL 累计统计后 **82.574 秒**。全部 1,968 个文件实际进入替换处理，六类 parser 标签都有记录，未发现解析 span 错误。

细分轮中，JSON.parse 执行 **1,432,363 次，累计 10.490 秒**。执行器 SQL API 累计约 39.25 秒，其中：

- 会话历史累计查询：**1,493 次、29.641 秒**。
- 用量事件 INSERT：146,412 次、约 **5.972 秒**。
- COMMIT：1,970 次、约 **1.868 秒**。

其余时间还包含解压、流读取、逐行调度、字段转换、指纹、其他 SQL 和启动。流/生成器 span 包含下游消费写库，不能把整个 span 全算成纯 JSON CPU；API 累计时间也不是互斥 CPU 采样。

累计查询形状为：

```sql
FROM events
WHERE session_id = ? AND home_id = ?
  AND source_path <> ? AND timestamp_ms < ?
```

查询计划实际选择 `events_home_idx (home_id=?)`。通俗地说，每次想知道某个会话之前的累计值，数据库先翻出这个 home 的大量历史，再筛选会话；重建时要反复做近 1,500 次。

实验只增加：

```sql
CREATE INDEX architecture_session_home_time_idx
ON events(session_id, home_id, timestamp_ms);
```

结果如下，两轮使用同样的 JSON/SQL/阶段探针：

| 指标 | 原实现 | 仅增加实验索引 |
| --- | ---: | ---: |
| 完整首屏 | 82.574 s | **52.030 s** |
| 累计查询次数 | 1,493 | 1,493 |
| 累计查询时间 | 29.641 s | **0.0169 s** |
| JSON.parse 累计 | 10.490 s | 10.319 s |
| 实际解析文件 | 1,968 | 1,968 |

两份实验库的 **146,412 条事件、71,153 条额度观测**，除数据库自增 id 外全部字段排序后 SHA256 一致；没有通过少解析、少存数据取得提速。索引仍只存在于私有实验库，未写入活动库或正式 schema。

这是“现有技术栈还有明显余量”的直接证据。它主要改善首次重建及相关会话追赶，不应把约 30 秒收益套到缓存命中的日常启动上。

空库重建只对正式实现及此索引控制做了实测，没有给四候选编造空库排名；四候选的完整来源对照是前述已有索引的两种状态。

## 原型为什么没有更快

P1 的一次无变化诊断首屏为 4.938 秒：初次变化流读取/传输约 **1.959 秒**，业务投影约 **0.900 秒**；首次取回 **142,498,349 字节**，准备了 160,862 个事件与 1,976 个来源贡献。只有后续小更新是增量，进程重启后的第一份视图仍需要重新加载、构造。

有变化时，还要额外核查源事实。代表性 P1 轮适配层用了 **2.427 秒**：保守检查 160,862 条事件，实际只发布 **13 个变化来源、约 500 KB**。这一成本属于当前桥接方式，已单列计入，没有从成绩中减掉。

无变化 u1 完成相同筛选序列后的进程树 RSS 样本：正式版约 **152 MiB**；P1/P2/P3/P4 约 **1,264 / 1,541 / 1,732 / 1,620 MiB**。不含浏览器，包含实验额外进程和当时仍保留的分配；这是活动结束后的一个样本，不是长期稳定值或峰值。

另外，P1 内核限制为 224 MiB old space 的诊断明确发生 **heap OOM、退出码 134、HTTP 500**。512 MiB 标准组通过，不能因此宣称低资源可靠性已经解决。错误与 fatal report 均保留在私有输出。

这些结果指向同一个问题：冷启动的全量事件搬运、临时对象和首次业务视图重建，抵消了存储内核的差别。没有理由把它包装成当前原型已经具备“极致性能且可靠”的优势。

## refact 应收敛成什么

1. **先处理累计查询的复合索引。** 实验已经验证收益和事实一致性；正式接入时补 schema 迁移、旧库开销及既有采集回归，不重写数据内核。
2. **持久化历史纪录和多周期业务视图，按来源/日期更新贡献。** source revision 变化后不要把所有视图都重新扫描；复用原型已验证的贡献合并思路，但保留正式版已经有效的持久摘要缓存。
3. **减少首屏阻塞工作和全量跨进程搬运。** 网页读取一致的已提交视图，采集/预计算后原子发布新版本；新数据刷新完成必须等到新版本显示，不能把旧缓存显示冒充更新完成。原型的 142 MB 首次变化流应改为直接读派生视图或受控分页。
4. **继续优化完整解析的数据通路。** 在现有文件事务、Zstd 验证、指纹复核及失败回退边界内，减少逐行 Promise/生成器往返和不必要对象，核对解压、转换与写入各自收益。原执行器 200 ms 空闲退场也应和视图复用一起评估，不能只保留短暂进程内缓存。
5. **暂缓全栈语言/存储替换。** 若上述调整后，剩余成本仍明确集中在 CPU 解码，再只为该段验证原生实现；当前原型没有独立重写六类 parser，不能据此推断 Rust 能把完整采集缩短多少。

## 验证、证据与复现

正式 `src/`、`public/` 的 87 个跟踪文件未改动；活动索引、真实来源文件和用户服务未写入/重启。所有 schema 实验和持久配置写入都在 `output/` 私有副本。

实验入口：`full-startup-run.mjs`、`full-startup-suite.mjs`；阶段探针：`startup-trace.mjs`；只读捕获/回放：`startup-inputs.mjs`、`startup-replay.mjs`；SQL/JSON 细分：`startup-sql-probe.mjs`；索引控制：`startup-cumulative-index.mjs`。来源事实适配有真实 Codex/DSH 夹具的替换与重复发布测试。

机器：i7-14700KF，20 核/28 逻辑处理器，约 32 GiB RAM，Windows 11 build 26200，Node v24.19.0。原页面、同一 Chromium、默认真实业务时钟。

私有证据根目录：`output/architecture-20261102/full-startup/`：

- `analysis.json`：全部结果、首屏前阶段、进程资源、8 组业务对拍。
- 每轮 `result.json`、API 原始响应、按 PID 的 trace/telemetry；原型另有来源 gate 和适配阶段日志。
- `empty-detail/aggregate-*.json`、`index-detail/aggregate-*.json`：完整 JSON/SQL 调用统计。
- `index-experiment-parity.json`：原始事实与额度观测字段哈希证明。
- `capture-pointer.json`、捕获 manifest、replay 报告、生产源码哈希及机器环境。
- 两次回放工具错误诊断以 `INVALID.json` 明确排除；缺失 WAL 的 `throwIfNoEntry:false` 语义已修正，并有 real/replay 指纹一致性回归测试。

已有捕获和种子时，可用 `pwsh` 执行：

```powershell
$env:ARCH_FULL_RUN_LABEL = 'new-repeat'
node experiments/architecture-20261101/full-startup-suite.mjs run
node experiments/architecture-20261101/full-startup-suite.mjs live
node experiments/architecture-20261101/analyze-full-startup.mjs
```

每次复测更换 label，避免覆盖已采集进程记录或混入旧 WAL；分析输出为 `analysis-<label>.json`。`run` 的标准批次不启用 SQL/JSON 重探针。详细轮在 `full-startup-run.mjs` 中通过 `ARCH_STARTUP_SQL_DIR`、`ARCH_STATE_SEED`、`ARCH_STARTUP_REPLAY_FILE` 选择，复合索引控制另设 `ARCH_STARTUP_CUMULATIVE_INDEX=1`。主加载器通过 `NODE_OPTIONS --import` 继承到正式 gateway 子进程和执行器，正式文件没有插入计时代码。
