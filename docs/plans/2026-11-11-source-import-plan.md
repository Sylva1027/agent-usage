# 数据来源自动扫描与确认导入计划

日期：2026-11-11，实施更新：2026-11-12。状态：**本地实现与双包验收已完成，当前源码服务已更新启用，并纳入 0.9。** 等待反馈为“阶段文字＋已用时间”，不加百分比进度条。下面第 2–12 节保留设计与原始基线，最终实施结果及回归波动见第 13 节；0.9 验收见[发布记录](2026-11-12-display-currency-plan.md#09-发布验收)。

## 1. 交付目标与固定边界

用户点击“数据来源／编辑”，自动扫描当前系统用户的常见记录目录；扫描成功后列出结果，由用户确认才开始导入。扫描无结果或失败时，展开手动选择及具体寻找方法。Windows 和 macOS 都能使用真正的系统文件夹选择器。

必须满足以下约束：

- 路径来自运行用户的 home、系统目录及环境配置，不包含开发者用户名或安装盘符。
- 扫描只发现和识别目录；不登记来源、不解析整段历史、不建立用量索引，也不因扫描触发后台导入。
- 已确认来源继续正常增量更新；新发现的来源等待“导入所选”。已有“是否参与统计”的勾选与新来源的待导入勾选使用独立状态。
- 保留已有历史、来源 ID、额度来源资格及用户筛选偏好；不能通过清库、重建全部历史或将所有来源改成 `extra` 来简化迁移。
- 只有可用结果已经发布到看板，才能显示“导入完成”。保存了目录不等于导入完成。
- 复用现有陶瓷质感弹窗、主题变量、滚动条与焦点管理。错误和寻找帮助按需出现，不增加常驻解释框、提示徽标或新的视觉体系。
- 本批不增加全盘搜索、后台定时发现新软件、导入任务中心、解析器重写或泛用队列框架。已封存的 TPS 不在范围内。

## 3. 本机耗时参考

本轮前序调查已经测量，每来源两次独立的新索引导入；不为写计划重复运行。环境为 Windows、Node 26.13.0、i7-14700KF、32 GB 内存。计时覆盖 `POST /api/imports` 后直到 `GET /api/usage` 返回可用 dashboard 汇总，不只测目录登记接口。

| 来源 | 记录规模 | 首次导入 | 已建索引后刷新 |
| --- | --- | --- | --- |
| Codex，静态副本 | 2,027 个日志、约 2.24 GiB；124,690 条事件、1,734 个会话 | **45.02–46.17 秒** | 0.590–0.632 秒 |
| DSH | 167 个文件；24,227 条事件、156 个会话 | **24.05–24.62 秒** | 0.094–0.109 秒 |
| WorkBuddy | 16 个文件；730 条事件、6 个会话 | 2.41–2.70 秒 | 0.026–0.028 秒 |
| Claude Code | 35 个文件；5,520 条事件、24 个会话 | 1.30–1.37 秒 | 0.041–0.049 秒 |
| ZCode | 1 个数据库；7,673 条事件、59 个会话 | 0.75–0.79 秒 | 0.025–0.030 秒 |
| OpenCode | 1 个数据库；526 条事件、11 个会话 | 0.42–0.47 秒 | 0.022–0.027 秒 |

六类默认来源的路径发现三次分别为 **0.0046、0.0032、0.0026 秒**。这说明现有本机目录发现与历史导入的开销相差很大，但不代表未来所有机器都能在数毫秒完成，也不是新增扫描接口的正式性能验收。

测量未清空操作系统磁盘缓存，不包含浏览器绘制及联网更新价格；两次样本只适合判断数量级，不能当作普遍 SLA。事件数不等于文件行数。各来源单独测量，不能直接相加作为批量导入耗时。

活动中的 Codex 原目录两次试验在 30 次重试后仍返回 `SOURCE_UPDATE_PENDING`；静态副本导入能完成。**根因尚未证实**，可能涉及源文件、辅助输入或发布校验，不能仅凭这一对照就归因为持续写日志。静态副本另有一条历史额度观察格式警告，事件导入完成。没有修改原记录。

### 进度展示选择

45–46 秒及 24 秒已经足以造成明显等待。用户已选择方案 A，使用现有反馈行显示阶段与耗时，导入期间禁用重复提交。方案 B 不实施：

| 方案 | 展示 | 实施范围 |
| --- | --- | --- |
| A：阶段与耗时 | 读取记录 → 建立统计 → 更新看板，显示已用时间 | 复用现有状态通知，增加必要阶段事件 |
| B：真实进度条 | 阶段、耗时及当前可准确计算的文件／字节进度 | 在现有 worker → server → UI 通道补进度；无确定分母的阶段使用不定进度 |

不按已耗时间猜百分比，不把不同大小的文件按等权数量伪装成总进度。只有目标版本发布并显示成功才完成；不搭建通用进度框架。

## 4. 用户交互与状态

沿用一个“数据来源”弹窗，保留已导入来源的统计开关；新增的候选区只承载本次待确认来源。入口不增加二次点击：打开即扫描，重试时才需要“重新扫描”。

| 状态 | 页面内容与控件 | 可产生的副作用 |
| --- | --- | --- |
| 扫描中 | 保留已有来源；反馈行“正在查找本机记录…”；导入禁用，关闭可用 | 只读探测 |
| 找到新来源 | 软件名称、实际目录、待导入复选框；新候选默认勾选；按钮“导入所选（N）” | 选择仅保存在弹窗状态 |
| 只有已确认来源 | 显示已有来源，反馈“没有发现新的记录目录”；导入禁用 | 不重复导入，不强迫手选 |
| 没有任何结果 | “未找到记录目录”，展开路径输入、选择文件夹和“如何找到记录目录” | 仍不登记来源 |
| 全部扫描失败 | 一句具体失败原因、重新扫描；展开手动区 | 与“目录不存在”区别处理 |
| 部分失败 | 保留成功候选；失败来源的帮助可展开，其他候选照常选择 | 单个目录错误不使整批结果消失 |
| 手动选择 | 系统选择器返回后只填充路径；“导入”是下一次明确操作 | 选择器不导入；取消不报错、不清空已有输入 |
| 确认校验 | 锁定提交按钮，服务端重新核实所选目录 | 全部条目通过后才一次登记；校验失败保留选择并指出具体项 |
| 导入中 | 保留弹窗和所选项；使用待选定的等待反馈 | 仅处理已确认批次，复用现有索引任务 |
| 成功 | 看板更新后反馈“已导入 N 个来源”；保留关闭按钮 | 不再次扫描或再次导入 |
| 导入失败／部分文件失败 | 保留目录、成功提交的事实及具体失败原因；可重试 | 重试幂等；不声称未发布的内容已经成功 |

成功扫描时手动区域默认收起，但保留低强调的“添加其他位置”入口，满足非默认路径用户；不会主动要求其手填。空目录若能识别其结构，仍可列为候选；是否有有效记录在导入阶段判断，结果为“该目录暂无可统计记录”，不能把它算成扫描故障。

关闭、Escape 或重复打开弹窗时取消前端扫描等待，并用请求序号忽略迟到响应；不会重新弹出窗口或自行导入。**已点确认的导入**不会因关闭弹窗撤销：关闭后用现有自动刷新状态显示简短状态，重开从服务状态恢复。此次不新增“中途取消并回滚全部历史”功能，也不把关闭按钮冒充取消。

已有来源的统计勾选仍立即生效；候选勾选只影响下一次导入。分别用“统计来源”和“发现的记录目录”两个简洁标签表达，不追加解释性卡片。导入尚在运行时允许查看旧数据；同一服务中第二次导入不并发修改来源集合，返回当前进行中的状态，结束后才提交另一批。

## 5. 扫描规则与路径身份

### 有限的候选范围

从 `options.homeDir`（测试注入）或 `os.homedir()` 解析 home，系统目录使用当前进程的 `APPDATA` / `LOCALAPPDATA` 等配置。下表是**需要探测的候选**，实际结构识别通过才显示为结果。

| 来源 | 探测规则 |
| --- | --- |
| Codex | 增加 `CODEX_HOME`；保留 `<home>/.codex`；两者不同且都有记录时分别展示并去重；保留 `CODEX_USAGE_HOMES` |
| JetBrains Codex | 复用现有 JetBrains 根目录及产品一级目录的 `aia/codex`，Windows 使用系统 AppData，macOS 使用 `~/Library/Caches/JetBrains` |
| Claude Code | `<home>/.claude`、现有 `CLAUDE_CONFIG_DIR` 和 `CODEX_USAGE_CLAUDE_HOMES` |
| DSH / ZCode / WorkBuddy | 现有 `<home>/.dsh`、`.zcode`、`.workbuddy-ai` 及各自 `CODEX_USAGE_*_HOMES` |
| OpenCode | 增加有效的 `XDG_DATA_HOME/opencode` 候选；保留现有 `.local/share/opencode`、AppData 与 macOS Application Support 候选；按现有支持的数据库／记录结构判定 |
| 项目用量日志 | 只探测明确配置或手动选择的目录及其 `.codex-usage/usage.jsonl`；不递归遍历所有工作区 |

`CODEX_HOME` 是 Codex 自身的状态目录配置，默认 `.codex`，见 [官方配置说明](https://developers.openai.com/codex/config-advanced/)。Agent Usage 可以同时发现旧默认目录中的历史，不能把“覆盖当前 Codex home”误解为应丢弃旧记录。OpenCode 等候选仍以当前 reader 能识别的结构为边界，不顺带承诺适配上游所有新存储版本。

复用 `discoverUsageSources`、各来源发现函数和 `classifyImportDirectory`。保留更具体的来源优先于 Codex、WorkBuddy 优先于 Claude 的分类顺序。需要内容判别时只读已有最小特征样本；审查现有 `LooksUsable` 的最坏读取范围，必要时提前退出。扫描期间不为了显示“多少条记录”遍历或解析整个历史。

默认目录不存在属于正常结果；权限拒绝、损坏或 I/O 错误保留为该候选的诊断。不能继续用当前通用 `exists()` 吞掉所有错误后统一说“未找到”。增加扫描所需的错误信息时保留既有解析器调用契约，不全项目替换文件访问逻辑。

### 规范化与去重

- 输入先验证字符串、非空、无 NUL，再处理首尾空白和复制粘贴的一对外围引号。相对路径不默默相对于服务安装目录解释，提示输入完整路径。
- 支持开头的 `~`，Windows 支持明确的 `%USERPROFILE%`、`%APPDATA%`、`%LOCALAPPDATA%` 前缀，按运行用户展开；其他未知变量提示完整路径。不使用 shell 展开、不执行用户文本。
- 对存在的目录使用真实路径辅助判断别名／junction，并统一分隔符和尾部分隔符。Windows 按文件系统身份去重，同时保留现有大小写兼容；不同目录不能仅因显示名相同而合并。macOS 不无条件小写化路径。
- 真实路径只参与重复判定，已有来源的持久 `id`、`kind`、路径身份不改写。迁移遇到此前已经登记的多个别名时保留既有身份，不擅自合并历史事件；新候选与任一旧来源匹配即不重复登记。
- 手动选择时返回目录身份，提交时再次检查。文件、错误层级、权限失败分别给出可操作提示；不要把选择单个 SQLite 文件当作选择 home 成功。项目 `.codex-usage` 目录仍沿用现有归一化到项目根的行为。

## 6. 后台来源边界与旧数据迁移

### 单一来源集合

Web 服务的 `usageOptions()` 生成已确认的来源描述，传给同一个 `discoverUsageSources` 入口。增加一个明确的“已确认来源集合”选项：**未提供**时保持 CLI 现行发现行为；提供空数组时表示 Web 尚未确认任何来源，绝不能退回默认自动发现。

这个选项在发现入口最早生效，不是“先发现全部、最后过滤报表”。以下调用必须得到同一集合：

- `/api/usage`、`/api/summary`、完整明细与快照创建；
- `UsageStore.syncRound`、fingerprint、`usage-summary-cache.readSourceState`；
- `/api/status`、watch roots、`requestUsageWake`；
- `usage-source-acquisition.beginFull` 的 `sourceCandidates`、homes 和辅助输入作用域。

未确认目录不得进入索引、监听根或 acquisition 证明范围。已确认但暂时缺失的路径仍保留身份及恢复监听需要的候选，不能把“本次未找到”当成用户移除。来源集合纳入现有缓存／acquisition context；集合改变时按现有失效机制更新，不再新建一套缓存版本系统。

CLI 的 `summary`、现有显式 `importDirs`、`CODEX_USAGE_IMPORT_DIRS` 及本工具专用的额外 home 配置保持既有显式配置语义。`CODEX_HOME`、`CLAUDE_CONFIG_DIR`、`XDG_DATA_HOME` 只提供应用存储位置，本身不等于用户在 Web 界面确认了新来源。冻结／历史导入运行实例继续遵守现有不可变边界，不对它们写来源选择。

### 持久化与迁移

沿用 `imports.json`，建议格式为 `{ version: 2, imports: [...] }`；每项保存必要的 `path/id/kind/label` 与既有导入属性。`imports` 在新版表示全部已确认来源，不另外维护第二份路径清单。派生的数据库／日志路径继续通过已有分类逻辑得到。

1. 首次新安装、没有旧来源清单和既有索引：建立空的确认集合；看板打开也不会自动解析本机历史，用户从“数据来源”进入扫描。
2. 旧安装首次升级：读取旧手动导入清单及已经索引／发布的来源元数据，作为已确认集合迁移。使用已有数据库和历史元数据读取入口；热索引、冷归档、暂时缺失的来源都要覆盖。不用全量原日志重建身份，不把升级时额外发现的目录顺手登记。
3. `main`、`jetbrains`、`extra` 等 kind 和原 ID 原样保留；尤其验证 Codex 5h/7d 额度来源与 `excludedHomes` 不丢失。环境覆盖出现新的 Codex 根时，以该根的稳定描述登记，不能重命名原 main 来源。
4. 先完整读取并验证迁移输入，再原子写新清单；失败保留旧文件和旧数据，明确返回失败，不回退为“全部自动导入”。迁移标记和集合在同一文件内提交，保证重启后不反复迁移。
5. 采用 [pricing-store.js](../../src/pricing-store.js) 的同目录临时文件加 rename 模式；新增、移除、迁移在同一个串行修改入口内重新读取、合并、写出，防止两个请求覆盖彼此。不要因此建立通用存储库框架。
6. 不支持两个服务进程同时拥有同一数据目录：沿用现有服务／数据库所有权限制，验证冲突时明确拒绝，不能只靠进程内 Promise 锁宣称支持多进程写入。

新版额外字段对旧版路径读取保持可读，但旧版仍会恢复其自动发现行为；回退演练必须说明这一差异。只保留必要的小型迁移前配置副本，不复制用户全部历史。原有“排除统计”和“移除导入目录”语义不在本批重设计；移除也不能删除用户的原始记录文件。

## 7. 接口、并发与完成语义

| 接口 | 计划契约 |
| --- | --- |
| 新 `GET /api/imports/discover` | 返回候选描述、是否已确认、各候选诊断及平台寻找提示；只读，不隐式同步或写选择文件 |
| 现有 `POST /api/pick-directory` | 继续返回 `{path}`；取消返回空路径；真实失败使用稳定错误码，前端本地化；不登记来源 |
| 现有 `POST /api/imports` | 兼容 `{path}`，增加 `{paths:[...]}`，两者同时传入报 400；重新分类、去重、整批校验后一次提交选择，再启动已有同步链 |
| 现有 `GET /api/imports` / `DELETE /api/imports` | 保留现有客户端必需字段和路径删除方式；适配已确认描述及串行持久化，不破坏旧调用 |
| 现有 `/api/status` 与状态通知 | 增加当前导入的目标来源版本、进行中／成功／失败与必要错误信息；复用现有 SSE 通知，不另建任务列表接口 |

批量请求继续使用现有 `readJsonBody` 的 16 KiB 上限，最多 64 个非空路径；拒绝非字符串、空数组和未识别目录。客户端提供的 kind/ID 不作为可信来源，服务端用已知描述或重新分类产生。路径通过 JSON/进程参数数组传输，日志与 DOM 显示均走现有转义方式。

新前端把 POST 成功理解为“确认已接受”，保留旧单路径响应字段，新增明确的进行状态及目标来源版本。只保留当前批次的一份小型内存状态，来源确认事实保存在 `imports.json`；不建立持久化任务表。重复提交相同目录复用同一同步，不重复解析已处理事件；其他批次在当前导入结束前不提交。页面刷新后从状态接口重新连接；服务重启后由已确认清单和现有索引恢复，不依赖旧浏览器内存。

完成必须同时满足：目标来源版本仍有效、该轮源事实及派生统计已通过发布校验、用量响应携带对应版本、前端成功渲染。旧缓存的 HTTP 200 不足以认定新导入完成。修改 `loadUsage` 对调用方返回可判断的结果，不能继续内部吞错、外层却显示成功。

提交前整批目录校验失败时不写半份清单；提交后某个记录读取失败时保留既有已提交事实，不做跨来源全量回滚。成功／失败明细以实际发布结果为准；未能发布时保留旧看板并显示未完成，重试复用现有增量检查点。断网、关闭页面或响应丢失后重试不得增加重复事件。

## 8. 活动文件与 `SOURCE_UPDATE_PENDING`

此项是正式交付前必须解决或给出明确失败路径的问题，不能用进度条掩盖。先在现有 acquisition／publication 测试夹具中分别复现：日志纯追加、已有内容改写／截断、目录增加、SQLite/WAL 更新、辅助路由／额度输入更新和来源集合改变；记录究竟是哪一项使发布校验失败。

目标是让一次导入针对可验证的读取边界完成，后续新增由下一轮增量接续。优先复用现有文件 offset、SQLite 只读事务和发布版本机制；纯追加只有在既有证据能证明已读取前缀未变时才能沿用。改写、替换、截断必须保留失效和重试，不以“到了 N 秒”强行发布。

如果证据显示现有实现无法在持续写入时收敛，再在最小责任层修复，补能失败的回归测试。不得提前以全量复制用户目录、要求用户停止使用客户端、降低一致性校验或无限加大重试次数作为正式方案。超时只是可重试失败，不是成功；合理期限在修复后以活动目录实测确定，并与“持续有进展”区别处理。

## 9. Windows / macOS 文件夹选择

Windows 采用系统现代 `IFileOpenDialog` 文件夹模式。复用现有 Rust 助手的构建、回执和打包链，增加独立的一次性 `pick-directory` 子命令；Node 通过 `execFile` 启动独立进程。**不在长期 source-proof 的 stdin 协议处理循环内打开模态窗口**，防止用户未选择时阻塞源校验或归档锁。

COM 使用单线程 apartment，启用文件夹／文件系统目录选项；只取真实文件系统路径。优先使用微软官方 `windows` crate 的生成接口，仅开启所需 COM/Shell 功能，锁定依赖；保留既有 `windows-sys` 证明代码，避免为了一个对话框手写 COM vtable 或大范围替换原生实现。依据：[Common Item Dialog](https://learn.microsoft.com/en-us/windows/win32/shell/common-file-dialog)、[Rust IFileOpenDialog 接口](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/UI/Shell/struct.IFileOpenDialog.html)。

一次性助手输出结构化 UTF-8 结果，取消作为正常结果，错误单独传递。没有额外控制台窗口；选择器本身正常可见。用户不需要安装 Rust、PowerShell 7 或开发依赖。Node 端只允许一个待处理选择器；关闭请求／服务退出释放自己启动的进程，后续迟到结果不覆盖新的输入。无图形会话或助手缺失时显示简短原因并保留手填入口。

macOS 继续复用 `osascript choose folder`，以参数传递默认目录和文案，不能把输入拼入脚本。实际验证中文、空格、取消 `-128`、隐藏目录和错误返回；当前注入 picker 的服务器测试不能作为 macOS 原生已验证的证据。Linux 保留扫描及手动路径，若无现有 picker 就如实降级，本批不额外引入 GTK/Qt 运行依赖。

手动帮助按来源列实际解析的候选位置。Windows 提示在资源管理器地址栏粘贴 `%USERPROFILE%\.codex` 等路径，选择的是目录；macOS 提示 Finder 的“前往文件夹”或选择器中的 `⌘⇧G`，输入 `~/.codex`，需要时用 `⌘⇧.` 显示隐藏项。扫描过的实际路径和其他来源位置放在可展开详情里，不在主流程塞完整排错文档。

## 13. 实施记录（2026-11-12）

### 行为和实现

- 自动扫描与导入分离，已有来源的统计勾选独立于待导入候选。零结果或失败展开手动区；成功结果保留轻量补充入口。
