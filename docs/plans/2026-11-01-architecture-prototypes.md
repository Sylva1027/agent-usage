# Agent Usage 架构原型实施计划

日期：2026-11-01；修订：2026-11-02

状态：四个运行原型已实现并完成 Windows 本地验证；当前先推进 Windows 重构与性能验收，Linux/macOS 适配后置。
范围：**4 个候选原型 + 1 个现状基线，共 5 组比较；桌面客户端原型为 0 个。**

2026-11-02 完整冷启动实测后，当前没有迁移胜者。后续实施主线改为[多 harness 与长期历史重构计划](2026-11-02-multi-harness-history-refactor.md)：一个正式候选、三个交付阶段，按历史增长曲线同时验收延迟、资源和可靠性。本文保留四原型的原始设计与实验边界，不代表其已具备完整替换条件。

本文是上一份交互式计划的 Markdown 阅读版，保留原型数量、实施范围和验收条件，并取代最初八条探索路线的实施建议。

## 1. 目标与边界

当前目标是在 Windows 上继续通过浏览器使用本地看板，通过可比较的实验选出能改善刷新与范围切换、同时保持可靠性的实现。Linux、macOS 在后续重构基本完成后，再集中进行适配和实机验证。

- **Windows 优先。** 当前原型完善、选型、重构、性能与可靠性验收均以 Windows 为目标；Linux/macOS 适配不作为本阶段的前置条件。
- **继续使用浏览器界面。** Rust 只作为本地后台服务的实现，本轮不开发独立 GUI、Electron、Tauri 或 WebView 客户端。
- **性能不能以可靠性为代价。** 不通过延后必要校验、降低检查频率、放松统计准确度或降低写入耐久性获取收益。
- **实验使用隔离环境。** 原型拥有独立数据目录和端口，不因实验替换正式服务、活动数据库或当前工作树。

客户端只有在测量证明浏览器已成为主导瓶颈后，才可能成为独立研究题。目前没有足够证据认定它能带来极致提升，因此本轮客户端数量为零。

## 2. 到底做几个，分别验证什么

| 编号 | 实现 | 对照对象 | 要回答的问题 |
| --- | --- | --- | --- |
| B0：现状基线 | 冻结当前工作树、输入和数据库一致快照 | — | 当前真实性能与业务结果是什么？ |
| P1：原型 1 | Node + SQLite + 新数据流 | B0 | 架构重构本身能带来多少改善？ |
| P2：原型 2 | Rust + SQLite + 同一数据流 | P1 | 换成 Rust 实现是否值得？ |
| P3：原型 3 | Rust + redb + 同一数据流 | P2 | 键值存储是否优于 SQLite？ |
| P4：原型 4 | Rust + DuckDB + 同一数据流 | P2、P3 | 列式分析是否优于前两种存储？ |

**B0 不算新原型；P2、P3、P4 共用 Rust 核心。**

比较关系如下：

```text
B0 当前程序
 └─ P1 Node + SQLite：改变数据流，验证架构收益
     └─ P2 Rust + SQLite：验证原生实现收益
         ├─ P3 Rust + redb：验证键值存储
         └─ P4 Rust + DuckDB：验证列式分析
```

“改变数据流”是四个候选的共同设计，不另算一种方案。语言是 P1/P2 的变量，存储是 P2/P3/P4 的变量。

Go、C#、自研数据库、PostgreSQL/ClickHouse 服务化、浏览器内数据库和桌面客户端不进入本轮实现。

## 3. 四个候选共用的数据流

```text
持续采集
  → 解析与必要校验
  → 提交事实及受影响的汇总
  → 发布一致的数据版本
  → 通知浏览器
```

范围切换查询已提交版本。用户主动刷新对应的新记录，必须完成校验、提交并显示后，才计为刷新完成。

已经校验的旧版本可以保持可读，但它只能算旧版本的读取响应，不能算新增内容的刷新成功。对无法证明安全的增量处理路径，保留完整核验回退，并把耗时计入尾延迟。

**撤回最初将“任意历史改写可以稍后发现”作为默认提速条件的建议。** 实施前先固定现有检查、发布与历史保留契约，再证明增量处理没有削弱这些要求。

## 4. 每个原型具体做什么

### P1：Node + SQLite，新数据流

**验证问题：** 只改变工作调度、数据组织与发布边界，刷新和切换能改善多少？

具体工作：

- 保留 Node 和 SQLite。
- 在隔离源码中实现常驻采集、读取进度持久化、受影响聚合维护、已提交版本查询和提交后通知。
- 复用现有六来源解释规则、定价/额度/TPS 公式、SQLite 工具、网页和测试。
- 复用已有 rollup，不另建通用缓存框架。

完成产物：

- 独立可运行服务。
- 六来源历史查询。
- Codex、DSH 原始记录追加到画面的完整链路。
- 与 B0 的业务结果、可靠性、延迟及读写量对比。

边界：这是实质架构改造。仅延长进程存活、降低刷新频率或直接返回旧缓存，不算完成。

### P2：Rust + SQLite，原生引擎

**验证问题：** 在相同数据流下，原生解析、紧凑数据结构和执行方式是否值得语言迁移？

具体工作：

- 以 P1 的逻辑事实格式和可见版本协议为契约。
- 使用一个常驻 Rust 服务实现采集、事务、聚合、查询和 HTTP。
- 尽可能保持 SQLite 逻辑表结构、索引意图、事务耐久设置与查询结果契约一致。
- 复用原网页。

完成产物：

- 完整服务请求路径，不在每次查询时启动 helper，也不通过临时 NDJSON 往返。
- 与 P1 相同的功能切片。
- 分别报告解析、入库、查询和整页时延。

边界：这里测量的是语言与原生实现的联合收益，不能宣称纯 Rust 语言加速倍数。六来源规范化回放与两来源原始日志测试分开计量。

### P3：Rust + redb，键值存储

**验证问题：** 事务型键值存储能否进一步降低刷新、查询与常驻成本，同时保持可接受的实现成本？

具体工作：

- 在同一 Rust 引擎内，将本项目存储改为 redb。
- 保存事件、游标、修订、有限索引、紧凑统计与发布版本。
- 复用 P2 的来源解析、业务规则、服务协议和界面。
- 只实现本轮查询需要的存储操作。

完成产物：

- 独立存储文件与恢复测试。
- 精确来源筛选、会话去重、TPS 分位数、价格修订和冻结查询。
- 与 P2 的性能、可靠性和维护成本对比。

边界：额外索引维护和历史修订成本必须计入结果。初版不同时引入 Parquet、自研 WAL 或第二种持久数据库。

### P4：Rust + DuckDB，列式查询

**验证问题：** 全部历史、自定义范围与多维筛选是否更快，同时普通追加和资源占用仍然合格？

具体工作：

- 同一 Rust 服务使用 DuckDB。
- 小批次提交输入，保持相同的发布语义。
- 将适合的筛选与分组留在列式引擎内。
- 复用 P2 的解析、业务规则、版本协议和网页。
- 保持逻辑数据相同，物理布局与 SQL 可以采用适合该引擎的做法，并记录差异。

完成产物：

- 大范围分析、普通小范围切换和并发追加的完整测试。
- 批次等待、后台整理、资源与端到端延迟报告。
- 与 P2、P3 的业务结果和恢复行为对比。

边界：不能为了吞吐量增加未计时的攒批等待。初版只使用 DuckDB 本地数据库，不叠加 Parquet 冷层或外部服务。

## 5. 统一的功能与数据范围

### 5.1 四个原型都覆盖的功能

- 同一网页与筛选操作。
- 今日、本周、本月、全部、自定义范围。
- 来源选择。
- token 和费用。
- 模型、仓库分组。
- TPS 的现有样本资格与精确分位数。
- 额度窗口。
- 暂停刷新后的范围切换。
- 新数据发布与重启恢复。

采用现有 API 的业务结果作为比较契约。测量插桩只记录时间和版本；所有候选采用相同的必要前端通知改动。

B0 保留现有触发方式，同时单独报告处理耗时，以区分轮询等待和计算耗时。

### 5.2 六来源查询，两来源完整增量链路

六来源冻结历史全部参与查询、筛选和业务结果逐项比较。

原始日志到画面的完整追加链路，第一轮覆盖：

- **Codex：** 当前关键来源。
- **DSH：** 压缩记录来源。

其余四来源第一轮使用从冻结原始数据得到的规范化事实回放，保留真实事件身份与字段。这不等同于已经移植它们的原生采集器。

胜者确定后，补齐其余四来源的实时适配。这是胜者补全，不增加第五条架构路线。完成六来源端到端验收前，不宣称可以替换生产。

### 5.3 公平比较的边界

- P1/P2 尽可能保持相同的 SQLite 逻辑表、索引与事务设置。
- P2/P3/P4 共享规范化事实、样本规则和精确计算契约。
- 允许 DuckDB 使用 SQL 聚合、redb 使用有限专用索引，但实现差异单独列明。
- 六来源规范化回放用于隔离存储与查询；Codex/DSH 原始输入用于端到端测量。
- 生成回放输入的时间不计入“存储与查询”实验，但不得用该实验声称已经测量完整导入速度。
- 完整链路计入全部读取、解析、校验、提交与显示。

## 6. 执行顺序与阶段交付

| 阶段 | 具体工作 | 交付与出口 |
| --- | --- | --- |
| S0：固定基线与契约 | 冻结当前源码、输入和历史库一致快照；复用测量与结果比较工具；定义异常与恢复场景；确认 Windows 测量环境 | B0 原始结果、源码/输入清单、业务预期结果、可复现命令 |
| S1：完成 P1 | 新数据流、增量校验边界、版本发布；跑通六来源查询和两个来源完整追加 | P1 与 B0 的可靠性、延迟、读写量对比；确定共同契约 |
| S2：完成 P2 | 原生核心、Windows 构建、相同 SQLite 行为；接入同一网页 | P2 与 P1 对比；Windows 构建和基础运行结果 |
| S3：完成 P3 与 P4 | 复用 P2 核心，分别实现 redb、DuckDB 所需存储与查询路径 | 两个独立可运行候选；完整功能与恢复结果比较 |
| S4：统一五组测量 | 在 Windows 串行轮换运行 B0/P1/P2/P3/P4；覆盖真实规模、扩展规模、并发与故障 | Windows 统一报告；胜出、落选或证据不足的明确结论 |
| S5：补全胜者，完成 Windows 核心重构 | 补齐其余四来源实时接入、历史迁移/备份/导入，以及 Windows 性能、可靠性与长测 | 胜者的 Windows 接入设计与可回退迁移包；不自动替换正式服务 |
| S6：后续平台适配 | 重构基本完成后，再处理 Linux/macOS 的构建依赖、路径、文件监听、生命周期与打包，并做实机验证 | Linux/macOS 独立的构建、功能、性能与恢复结果 |

S0–S4 是 Windows 上固定的四原型验证；S5 仅在有合格胜者后进行。核心数据流、业务汇总和主要来源接入基本稳定后，再进入 S6。Linux/macOS 的环境准备、适配和验收不阻塞当前阶段。

当前下一步是在 Windows 上打通真实看板的快速查询链路，再进行五组端到端性能初筛：定位采集、校验、提交、传输、业务计算和显示耗时，避免用基础聚合接口耗时代替整页体验。

### 工作量控制

- 四个候选各实现约定的功能切片，不移植全部设置界面、皮肤、安装器或无关功能。
- P3/P4 可以独立开发存储部分，但性能试验必须串行；共用文件保持单写。
- 是否并行派代理按会话授权执行，不把多代理作为计划前提。
- 每阶段交付可运行产物、命令、结果与未通过项。编译通过不等于功能完成。
- 不追加未经说明的新路线。
- 某候选出现 Windows 运行障碍或可靠性失败，先记录失败并尝试在本方案内修复；仍不合格则淘汰，不为凑数量删除检查。已知的 Linux/macOS 差异记入 S6，不作为当前选型的淘汰条件。

## 7. 性能目标与测量方法

### 7.1 初始验收目标

以下为工程目标，**尚未实现或测得**。

| 指标 | 初始验收目标 | 测量边界 |
| --- | --- | --- |
| 已有索引范围切换 | p95 ≤ 200 ms | 点击到完整目标版本可见；包含全部范围、自定义范围和来源组合 |
| 普通追加可见 | p95 ≤ 1 s | 可解析记录写入到其精确增量显示；包含通知、等待、校验、提交与绘制 |
| 已有数据重启首屏 | ≤ 1 s | 上个完整版本的首屏；新输入追赶另报，不能充作实时刷新 |
| 小增量扩展性 | 新增量固定时，稳定历史处理不随总量明显增长 | 1×/5×/10× 历史；报告读取字节、处理事件/依赖数与延迟曲线 |
| 后台工作时交互 | 报告同样的 p50/p95/max | 持续导入、修订和整理时切换范围；必须保持正确版本 |
| 资源 | 据实比较，不通过失控资源换速度 | 服务进程树、浏览器、CPU、内存、I/O、磁盘增长与恢复时间 |

以 B0 冻结清单中的实际规模为 1×；之前实验中的 3.52 GB 仅为参考。上游尚未写出记录的等待另列。首次全量导入单独测量。

### 7.2 固定测量方法

1. 每种高频场景、每组至少采集 100 个有效样本，报告 p50/p95/max。
2. 按候选轮换顺序测量，记录机器负载与冷热状态，不并行压测候选。
3. 扩展数据使用新的事件、会话和来源身份构造，避免简单复制后被去重，制造虚假的大规模结果；区分真实数据与合成扩展。
4. 对源写入、采集、校验、事务提交、版本发布、HTTP 和可见帧分别打点。
5. 旧缓存、半成品结果或先关闭转圈，不算刷新完成。
6. 每个通过功能门槛的候选，做至少一小时混合负载稳定性试验。
7. 胜者补全后，再做至少八小时长测，覆盖冻结、追加、修订与重启。
8. 当前统一在同一台 Windows 机器上比较各候选，记录进程树的 Working Set、Private Bytes、CPU 和 I/O。
9. 后续适配阶段在 Linux/macOS 上复用同一场景，在各平台同一台机器内比较，不跨硬件直接比较绝对耗时；Windows 的 Private Bytes 不与 Linux RSS 直接等同。

## 8. 可靠性验收条件

### 8.1 业务结果一致

完整比较 `summary`、`metadata`、`periodComparison`、`pricingCatalog`、`quota` 与 TPS 业务字段。

token、费用与精确分位数，不通过额外容差或近似算法过关。版本编号、路径和固定时钟等实现差异，必须在比较契约中逐项声明；不能删掉业务字段或把异常返回当作成功。

跨语言费用累加次序如造成差异，要修复或明确记为未通过。

### 8.2 写入与恢复

在写前、事务中、提交后发布前注入进程终止，验证：

- 重启后已确认数据不丢失。
- 重放不重复计数。
- 不发布半个版本。
- 提交耐久配置保持同等级。

不得通过关闭同步写盘、移除约束或仅存内存提高成绩。

进程终止、写入失败和可控 I/O 故障测试，用于验证程序恢复路径，不冒充真实断电或硬件故障验证。

### 8.3 来源异常恢复

以下情况都需要明确预期结果和恢复验证：

- 半行、坏帧。
- 截断、替换、重命名。
- 同大小、同时间戳的内容改写。
- 漏通知。
- 迟到计时。
- 失联来源。

### 8.4 校验与发布

先固定现有检查和发布契约。增量优化需要证明，只重算受影响范围仍得到相同结果；无法证明时执行完整校验，并将耗时计入性能结果。

### 8.5 历史与冻结

- 上游已删除、但本项目保留的事实仍然存在。
- 暂停刷新后，所有区块和范围切换绑定同一版本。
- 改变价格、来源或时区时，按现有语义重新发布。

## 9. Windows 优先与后续平台适配

### 9.1 分阶段运行矩阵

| 平台 | 执行阶段 | 需要实际运行的内容 |
| --- | --- | --- |
| Windows x64 | 当前 S0–S5 | 构建、六来源业务、真实看板性能、路径/文件替换、监听恢复、冻结、迁移与长测 |
| Linux x64 | 核心重构基本完成后的 S6 | 构建依赖、路径与监听适配，同一业务夹具及性能/恢复验证 |
| macOS ARM64 | 核心重构基本完成后的 S6 | Apple Silicon 构建、平台适配，同一业务夹具及性能/恢复验证 |
| 其余架构 | 后续明确支持范围时安排 | Linux ARM64、macOS x64、Windows ARM64 单独记录适配与实测结果 |

当前以已具备的 Windows 环境推进。Linux/macOS 暂不安排适配或测试；进入 S6 后以实际运行结果验收，交叉编译成功不等于运行可靠。

### 9.2 实现与验证安排
