## 已知证据与定位目标

上个验收包的失败并非“运行15分钟才积累出来”：前15分钟是预设普通／突发日程，进入每5秒一次的连续写入后约24秒失败。可直接重现该交错，不必重跑前面的等待。

| 已核实的链路 | 证据 | 仍需短测试确认 |
|---|---|---|
| 首次失败在DSH | 请求39：Codex已提交1个来源；DSH在`sourceProof.verify`发现stat与发现时不符；整轮约6.16秒 | 已提交部分和失败事务、进度、派生状态如何影响下一轮 |
| 随后Codex也失败 | 请求40：约4.61秒后在同一检查点失败，尚未写入该来源；`/api/usage`最终HTTP500 | 主动查询和后台唤醒交叠如何传播失败 |
| 错误未获恢复 | `UsageStore.sync`仅对`SOURCE_COVERAGE_UNAVAILABLE`有特定重试；`LIVE_SOURCE_CHANGED`直接上抛 | 应在什么最小边界重新观察来源并重试 |
| 唤醒可能丢失待办 | `requestUsageWake`捕获错误后将`usageWakePending=false`并返回 | 失败前到达的通知是否被消耗；无后续通知能否自动补齐 |

文件真的在变化，来源保护抛错本身合理。要修复的是过期观察的恢复、待处理工作的保留和对外完成语义；不删除size／mtime／ctime、内容或原生证明检查。

## 一张卡，三个顺序步骤

### 1. 用短夹具复现并确定恢复边界

复用现有Codex／DSH输入、事务与小型冷热混合夹具，通过可控Promise暂停点，在“发现后、验证后、提交前、一个来源提交后”精准插入真实文件追加。避免靠sleep碰撞；超时只作为测试失败上限。入口走真实同步、执行器和HTTP，保留数据库事实／游标／发布标识断言。

产物是可复现测试和一张简短时间线：哪条记录已提交、哪个来源观察过期、哪项通知仍待办、哪个HTTP请求受到影响。旧版须命中原来的两条失败路径；若无法复现，停止修改生产代码，先纠正夹具，不扩大到长测。

### 2. 修复来源竞争的恢复与发布

优先在现有来源处理循环内解决，保持一个共享同步任务：

1. 对已确认的暂态来源变化，失败来源事务完整回滚后重新读取该来源信息，重新验证并处理。**每个来源在一轮内最多初次＋2次重试**；不在旧事务内重试，不让HTTP、执行器和来源层各叠一套重试。
2. 已提交的其他来源保留；继续使用已提交解析检查点，避免重复计数、重复累计价格或反复插入相同事实。检查跨文件累计依赖、警告与工作计数在失败尝试后是否正确恢复。
3. 新读取的信息必须与来源指纹、解析字节边界、采集凭据和最终发布对应。不能只替换`file.info`，再用旧计划的指纹宣称全部同步完成。复用现有采集完成／失效和发布守卫。
4. 超过本轮重试上限时保留待办，合并后续通知并让出执行权；每次只留一个后续任务，禁止立即递归空转。无新通知也应继续处理已知待办。仅在完整一致的新版本可用后通知“同步完成”。
5. 正常连续追加应在内部恢复，不向页面泄露HTTP500。若刻意不断改写，始终无法取得有效快照，使用明确的可重试忙碌状态，不返回旧值冒充刷新完成；页面沿用现有刷新过程。该边界也必须被短测试覆盖，不能靠无限延长请求超时解决。
6. 仅将真实来源变化纳入这一恢复路径。同一错误码目前还覆盖无效大小、非法解析边界等情况，需检查具体原因，必要时补最小内部分类。权限、磁盘、数据库损坏及无效输入仍保留真实错误，不能笼统吞掉。

不预设新调度框架、持久队列表或通用重试库。若第一步证明来源内重试不足，才在同一张卡中补足现有同步／唤醒协调边界；新增行为仍限上述恢复契约。忙碌状态的传递如需触及前端，只接现有加载／重试状态，不加常驻警告、徽标或说明框。

### 3. 小测试通过后，做限定页面保护与持续写入验证

固定工作量：**16个确定时序业务用例＋6个原页面短对照组**。两年候选组的常规保护测量结束后，追加一个3分钟连续写入段；不另开长测矩阵。

## 确定时序用例：8场景 × Codex／DSH

| 场景 | 如何触发 | 必须满足 |
|---|---|---|
| 1. 发现后又追加 | 阻塞验证入口，追加，再放行 | 刷新来源观察后恢复；新记录只计一次，正常HTTP成功 |
| 2. 验证后又追加 | 在解析／最终capture之间追加 | 当前尝试事实、进度及派生写入回滚；重试与完整解析oracle一致 |
| 3. 前一来源已提交 | A提交后让B变化；分别交换Codex／DSH角色 | A不重复计数，B不漏计；未完成整轮不得错误发布“已同步” |
| 4. 连续变化超出本轮预算 | 连续使3次尝试失效，然后停止写入且不再发通知 | 无忙循环；待办未丢；自动收敛，超限不伪装成功 |
| 5. 多标签与通知交叠 | 三个请求、SSE／status检查及重复提示同时到达 | 合并同一同步；价格、事实、版本一致；只在完成后清除刷新状态 |
| 6. 非追加修改 | 截断、等长旧内容修改／替换 | 原证明失效，按既有规则完整重处理；不误当成安全追加 |
| 7. 部分提交后进程退出 | A提交／B未完成／整轮未发布时终止执行器，再重开 | 检查点可恢复，事实和金额不丢不重，冷热查询一致 |
| 8. 真正故障与取消 | 注入权限／存储错误；另验证等待中关闭服务或切换请求 | 真错误不被当成功；任务、事务、读者及工作进程持有能释放 |

这里的16是参数化业务用例数，不把内部断言数量或重复运行次数当覆盖。病例1、2强制SHA路径；原生证明通过现有真实助手专项回归，不能用SHA替代原生结果。现有proof、Codex/DSH进度、跨文件依赖、采集、发布、SSE／多标签和关停相关测试只跑受影响范围，最终版本统一跑一次；必要的失败用例随修复重跑，不反复跑全套找绿色。

常规组共18条追加、6次重开；连续段36条追加、1次额外重开，总计**54条追加、7次重开**。连续段不得混入普通刷新对照或用来挑选更快结果。范围切换保留现状，不重新追200ms；自定义日期优化继续冻结。

复用保留的三种布局、种子与当前工作状态，顺序运行，固定价目及后台检查条件，两版顺序交错；计时期间不并行构建、扫描或跑测试。只保留循环使用所需回滚副本，不为每个样本复制整套历史。真实数据下的初始化、恢复和oracle开销单列；3分钟是连续写入时长，不冒充整个验收仅需3分钟。
