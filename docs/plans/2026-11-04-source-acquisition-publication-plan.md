## 1. 决定与交付边界

**一条候选路线，三张顺序任务卡：确认变更依据 → 改造采集和发布 → 验收。** 不再并行比较语言、数据库或客户端方案。

本阶段解决的问题是：一次普通追加仍然反复触发来源发现、全体文件指纹和发布检查。把“发现并处理变化”集中到一个采集入口，查询消费它已经确认的版本。增量业务计算继续复用 B2、Q1–Q4 的成果。

首个快速通路覆盖 **Codex 普通 JSONL 和 DSH 的现有帧格式**。六种 harness 的查询结果、历史保留和回退路径全部保留。其余来源发生变化、来源拓扑不明或证明不完整时，继续使用现有完整同步；不以仅检查 Codex/DSH 冒充六来源都已检查。

完整重建是另外一次交付，本阶段不同时更改解析算法、批量写入及首次派生算法。它们和采集调度有不同的成本，混改会再次让归因失去可信度。

## 2. 已知事实与唯一待验证的前提

| 事实 | 对方案的约束 |
| --- | --- |
| Q5 的 10× 原生 Codex 正确新值实际绘制中位数为 2.935 秒；一个样本来源同步 1.961 秒，实际追加 69 ms | 有理由改采集组织方式，但不能把全部差额都算作目录扫描 |
| 同步前、同步内、部分查询后的发布检查各自有来源发现或指纹工作 | 快速通路应复用一份有版本边界的检查结果，删除重复工作 |
| SHA 路径一次追加约解析 570 字节，却重读约 4.04 GB 旧前缀 | 调度改造不能消除没有变更依据时的旧内容验证成本 |
| 当前原生助手针对一个已知文件提供旧前缀证明 | 它尚不是“这个目录只有这些文件改变了”的完整变化清单 |
| `fs.watch` 当前丢弃具体路径，只负责唤醒；通知可能缺失 | 保留路径能帮助调度，通知本身不能授权跳过其他来源 |
| 现有执行器每次追加通常重新启动 | 本阶段保持既有进程数量和退出策略，启动时间计入结果；不预设延长存活就是答案 |

**需要先回答的唯一能力问题：普通用户权限下，能否在连续两个检查边界之间，取得受管来源的完整变化集合，并证明没有遗漏？** 这里包括新建文件、目录移动、持续打开的写入句柄以及已知文件修改，不能只处理收到通知的路径。

Windows 的变更日志会合并同一打开周期内的重复变更，并可能淘汰旧记录；因此“读完日志，没有新条目”不自动等于“没有新写入”。这是文档明确的行为，见 [Microsoft：Change Journal Records](https://learn.microsoft.com/en-us/windows/win32/fileio/change-journal-records)。现有助手使用的 [强制 close 记录](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_write_usn_close_record)可以提供单文件边界，但不能未经验证就推论整个目录的覆盖成立。

Q5 已知 C 盘具备原生证明条件，E 盘 journal 不可用；本阶段不重新探索是否启用 journal，不改变系统配置。原生路径和 SHA 路径始终分开报告。

## 3. 任务卡一：限时确认完整变化清单

**投入上限：60 分钟，包含最小验证工具的编写和运行。** 只使用隔离小文件、现有原生助手和当前 Windows API；不复制 42 GB 数据、不完整导入、不启动浏览器矩阵。若在这个额度内无法给出成立条件和反例结果，结论就是“前提未证实”，本阶段停止，不进入后两张卡。

检查以下 **8 组情形**；每组包含确定的文件操作、预期变化集合和实际返回集合：

1. 同一个写入句柄持续打开，连续追加 20 次；覆盖服务启动前已经打开的句柄。每个检查边界均能看到该边界之前的已完成写入。
2. 追加与旧内容原地改写混合，恢复 mtime，确认不会错误接受“仅追加”。
3. 截断、删除后同路径重建、同大小文件替换，确认文件身份重新建立。
4. 新建嵌套目录和文件、父目录改名、目录移入/移出来源范围，确认来源清单不会漏项。
5. 硬链接及其他路径别名写入；不能证明的重解析点/外部目标明确回退，不能默默跳过。
6. 丢弃所有 `fs.watch` 通知、传入未知文件名、重复通知和事件合并；手动刷新及既有周期检查仍能恢复真实变化。
7. journal 缺失、游标过期/重置、权限不足或助手异常；返回“覆盖不成立”，保持原回退。缺口/重置使用受控协议夹具，不更改真实卷配置。
8. 扫描中继续写入、扫描后重启、处理完成前重启；变化保留在本轮或下一轮，未完成游标不会冒充已处理。

通过条件不只是“8 组没有报错”。必须写清楚检查区间、目录身份、持续打开文件的处理、游标有效期及未知路径的回退条件。持续打开文件若必须逐个检查，只允许工作量随**可证明完整的活动集合**增长，不能把所有历史文件永久留在活动集合，也不能靠超时猜测文件已经关闭。

**失败后的确定动作：保存最小反例和能力结论，停止实施并汇报。** 不临时改成每隔几分钟后台全扫、长期持有全部文件句柄、管理员服务、驱动或修改 harness 写入方式来维持原来的性能承诺。

## 4. 任务卡二：一条采集通路和一个发布结果

仅在卡一通过后实施。路线固定如下：

```text
文件提示 / 手动刷新 / 既有周期检查
                  ↓
        一个采集入口确定检查边界
                  ↓
   完整变化清单 + 仍需检查的活动来源
                  ↓
 Codex/DSH 增量读取 + 受影响的跨文件依赖
                  ↓
     既有事实、进度与持久业务视图
                  ↓
   完成本轮检查，发布一致版本与通知
                  ↓
       原页面查询该版本并绘制新值
```

### 4.1 来源清单与调度

- 由现有采集入口统一持有变更区间、来源归属及辅助输入。提示携带来源根、路径和事件种类，重复路径合并；未知路径转为必须核查的范围。
- 已知来源事实、解析进度和跨文件依赖继续使用 `source_files`、`usage_source_progress`、`usage_source_baselines`、`usage_source_reparse`。
- 若目录身份映射确需持久化，最多新增**一个可重建的目录清单表**，只存对象身份、父目录、路径和所属来源；小型检查游标/发布状态复用 `store_meta`。不再建立一套事实库或事件总线。
- 变化很多时分批读取清单，内存不积累无限路径集合。超出可证明的覆盖或处理预算时明确回退，不能截断变化列表后继续成功。
- 只有本轮所有启用来源及相关输入都有有效覆盖，才能使用整轮快速通路。未覆盖的导入目录、其他卷或辅助文件会使本轮使用原有检查流程；混合环境的回退成本照实计量。
- 其余四种 harness 发生变化时，本阶段走既有完整同步。SQLite 来源仍保留编辑/删除语义，不以 `MAX(id)` 判断无变化。

### 4.2 增量执行和恢复

- Codex 使用现有完整行边界和累计解析状态，DSH 使用现有完整帧边界；逐文件原生证明和 SHA 回退继续绑定实际解析的字节。
- 变化文件之外，还必须处理 `usage_source_reparse` 中的依赖。不能因为新调度只选中了一个文件而漏掉同一会话后续文件的累计基线修复。
- 游标只在对应区间的变化处理、必要依赖修复及发布核对全部完成后推进。事实已提交但游标尚未推进时，重启重新检查该区间，通过既有来源进度避免重复累计。
- 原始来源暂时失联仍保留已有历史；改名和替换继续遵守现有去重规则。
- 同步过程中再来的变化保留到后续区间；一轮处理的是明确的有限边界，不无限等待所有来源安静。

### 4.3 发布和查询

- 本轮返回一个包含已检查来源区间、事实修订、证据/配置依赖及完成状态的结果，供服务器、响应缓存和 SSE 共用。价格、时区、时钟到期继续独立参与原有查询有效期。
- 快速通路不再让同步前、同步后和查询后各自重新发现全部来源。用已证明的检查区间和必要提交复核替换重复发现；不能直接删掉复核。
- 范围切换消费已发布数据，不再发起新一轮原始来源检查。手动刷新和自动采集完成，仍必须等新值对应的事实与所需业务结果可用；旧缓存不算刷新完成。
- 同步中的读取复用现有已发布读视图和一致缓存。没有可读的完整版本时等待提交，不拼接两个版本。本阶段不承诺任意复杂查询在长时间修复中也能立即完成。
- 保留数据库外部写入检测、冷包核验、发布缓存保护和价格一致性。新“版本号”不是取消这些保护的理由。
- 继续使用现有执行器和原生助手，不新增长驻服务或读取进程，不放大堆。首次目录初始化另计；服务重启后的状态来自磁盘，不依赖无限常驻缓存。

### 4.4 预计改动范围

| 位置 | 改动目的 |
| --- | --- |
| `src/usage-source-watch.js` | 保留路径/来源提示及未知范围，不把提示当完整证明 |
| `src/usage-source-native.js`、`native/windows-source-proof/src/` | 在卡一确认的能力内复用原助手取得完整变化区间，保留单文件证明 |
| `src/usage-core.js`、`src/usage-store.js` | 来源清单、受影响文件和依赖的选择；复用现有解析与写入 |
| `src/usage-source-progress.js` | 仅在必要时接入持久检查进度，不重复实现解析检查点 |
| `src/server.js`、`src/usage-summary-cache.js`、`src/usage-executor.js` | 一轮检查结果复用、版本发布、查询和刷新调度 |
| `public/app.js` | 仅在版本交接需要时调整请求参数/完成条件，页面外观不变 |
| 既有来源、缓存、执行器、通知与恢复测试 | 覆盖新入口，旧路径继续回归 |

不扩展计价公式、额度规则、汇总算法或冷历史结构。若实现必须增加第二套事实存储、永久读快照或另一组业务算法，视为超出本阶段，不静默扩大范围。

## 5. 任务卡三：固定规模验收，不边跑边扩矩阵

2026-11-05 用户批准缩减：主对照 8 组，每组 Codex/DSH 各 2 次，共 32 次追加；文件数对照 4 组，每组两种来源各 1 次，共 8 次追加。合计 **40 次追加、24 次范围切换、8 次服务重开**。没有空库真实历史重建。先完成原生组；若候选超过一半追加依赖完整回退，或 10× 原生任一来源改善不足 15%，停止剩余组并报告原因，不自动追加样本。15% 是继续测试的方向门，既定 30% 刷新验收目标不变。以下旧数量仅保留原始计划依据，以本段缩减口径为准。

先完成小夹具与受影响回归，再冻结候选代码运行性能比较。对照固定为 Q5 提交 `04aadc2`；复用既有原始数据和种子数据库的隔离副本。所有目录/硬链接提前准备，避免后续建镜像改变认证时间戳。价格、数据与查询口径一致。

| 验证 | 固定数量与目的 |
| --- | --- |
| 原页面普通追加 | Q5/候选 × 1×/10× × 原生/SHA，共 **8 组**；每组 Codex 5 次、DSH 5 次，共 **80 次追加** |
| 原页面范围切换与重启 | 每组 today/week/all 等既有常用范围共 10 次切换、1 次服务重开；共 **80 次切换、8 次重开** |
| 独立文件数增长 | 同一小型逻辑数据重分布成约 2,000/20,000 文件，Q5/候选共 **4 组**，每组 5 次追加，共 **20 次追加**；隔离文件数成本，不复用“事件密度等于年份”的说法 |
| 中断恢复 | 原生/SHA × 事实提交前/事实提交后但发布游标推进前，共 **4 个强制终止点**；恢复后的结果与完整同步对拍 |
| 正确性 | 六来源业务字段、已删除原文件的保留事实、跨文件累计、迟到修订、价格/证据变化、冷历史回退、漏通知和并发请求，使用小夹具和已有回归；类型检查、lint、完整回归各一次 |

**本阶段计划 100 次计时追加，0 次空库完整重建。** 初次来源清单建立、旧库升级、恢复与回退耗时独立记录；源数据准备也记账。普通刷新测试不再靠重建整份事实库获得起点。

耗时主指标是“记录完成写入 → 原页面绘制正确新值”，同时记录 SSE 和探针确认时刻，不能混用。性能轮保持最小计数，详细分段只用于小夹具定位；避免再次把大规模诊断插桩当作未插桩的产品速度。

固定矩阵后，如出现解释不了的差异，只允许增加**一组针对已有假设的小诊断**，记录目的和上限；若仍解释不了，保留未达标结论，不无限补样或改换对照口径。正确性失败先修复，并重跑受影响项，不能以次数上限为理由跳过。

### 验收门

下列均为目标，尚非实测结论：

- **结构门：** 原生覆盖成立的普通追加，不遍历全部历史目录、不为全部来源文件重新算内容指纹、不读取无变化文件的历史正文。工作量随变更区间、活动来源和真实依赖增长；必要 journal 读取、辅助输入和初始化单列。
- **刷新门：** 10× 可靠原生路径下，Codex、DSH 各自正确新值绘制中位数 **≤1.5 秒**，且相对本轮同口径 Q5 至少降低 **30%**。这是下一阶段门，主计划的一秒长期目标仍保留。
- **增长门：** 固定活动来源与追加量，1×→10× 密度增长、2,000→20,000 文件增长分别检查，中位耗时比例目标 **≤1.3**，同时确认没有转移成全历史后台扫描。
- **查询门：** 无新变化时常用范围切换不读取原始来源，绘制中位数目标 **≤200 ms**。本轮样本量不宣称完成正式 p95 或长期验收。
- **回退门：** SHA 及不支持环境的结果、检测和恢复语义不变，同轮中位耗时回退不超过 **10%**。SHA 长前缀仍必须验证，不承诺本阶段也能降到 1.5 秒；该限制必须进入最终结论。
- **资源门：** 堆保持 gateway 512 MiB、executor 224 MiB / semi-space 4 MiB；服务树活动峰值 **≤512 MiB**、空闲工作集目标 **≤256 MiB**。CPU、逻辑读写、目录索引大小、WAL 和浏览器内存一起报告，不能把工作移到后台后漏计。浏览器单列。
- **正确性门：** 结果精确对拍、失败不推进完成版本、重启不遗漏/重复、所有预期回退可辨认。既有测试失败与新回归分开记录。

只要完整变化集合或发布一致性不成立，就不进入性能验收。性能门没过就明确写没过，不用“代码已经重构”替代完成目标。

## 6. 完整重建的后续位置

本阶段收口后单独决定完整重建的实施卡。确定的职责边界是：**专用构建任务读取输入 → 有界批量导入 → 必要派生一次初始化 → 完整结果发布**；日常刷新不调用这条流程。
