## 目标和已有证据

**已校验并提交的一批数据可以先显示，之后到达的写入继续作为下一批待办。** 例如第100批已处理完，第101批刚到达：发布第100批，接着处理第101批。完成的是有明确输入边界的一批，不宣称外部来源已经停止变化；尚未处理的新输入也不能靠旧缓存冒充完成。

上一卡真实两年连续段中，10轮同步约15.7–17.7秒，9次来源竞争均有后续同来源提交，轮级／同步级没有继续抛来源错误；HTTP却出现22个409。36条直到末次输入后26.680秒才在同一个版本显示，写入期间完成版本为0。16个短用例覆盖了有限冲突恢复，缺少“每次提交后、绑定发布前再次写入”的持续交错。

代码中至少有三个必须一起核对的位置：

| 位置 | 当前行为 | 本卡必须证明 |
|---|---|---|
| `server.loadUsageStore` | 恢复后的指纹改变时，要求同步后再次读取的原始来源指纹与已提交指纹相等，否则409 | 后续输入可保留待办；已提交批次的身份不因此作废。配置／证据等辅助变化仍按原保护处理 |
| `/api/usage`、`/api/summary` | 响应前再查来源，重叠同步还可能重试或让`usageVersion`为空 | 实际返回的事实、费用、元数据、周期与版本属于同一次一致读取；仅修第一个409不够 |
| 后台唤醒／页面读取 | 后台可立即开启下一轮，`loadUsageStore`又先等待`syncPromise` | 已等待的查询能读取完成版本，不能总排在后续同步之后；慢标签不能阻塞整个采集 |

上述是代码依据与定位假设；既有日志没有记录每个409究竟命中来源还是辅助输入比较。第一步将补足这一因果证据，不把所有等待先归为同一种错误。

## 一张卡，三个顺序步骤

### 1. 精确复现发布饥饿

在现有小型冷热夹具和故障钩子里设置可控暂停点：来源验证结束、整轮提交完成、绑定发布之前、查询已取得快照、响应发送之前。用Promise握手安排下一条真实Codex／DSH写入，不靠随机sleep碰撞。

固定复现三代输入：N提交后马上写N+1；N+1提交后再写N+2。分别覆盖有、没有来源层重试的路径。旧版应稳定命中409／空版本／查询持续等待中的实际分支。只记录批次、事实指纹、辅助依赖、执行器身份、请求与通知时序，不增加常驻日志或UI说明。

定位输出是一条可检查时间线：本轮输入观察→来源提交→整轮成功→发布判断→HTTP／SSE→真实页面绘制，并注明下一批待办。若小夹具未复现，就纠正暂停点；不先跑大数据或修改守卫。

### 2. 把完成版本与下一批待办分开

1. **固定本轮完成边界。** 复用来源实际校验／消费到的边界及现有数据库事实版本；源文件在之后继续追加，不改变已完成批次的身份。带检查的刷新必须覆盖本次已观察并交给同步的输入，不能直接返回更早一批。外部文件没有全局原子时钟，不把这个边界描述为所有来源在某一纳秒的完整快照。
2. **由持有数据的执行器证明完成。** 优先扩展现有完成采集凭据与数据库守卫，携带小型内部批次身份、事实版本和辅助依赖，查询结果带回其实际读到的版本。用原有SQLite／冷热投影读快照保持结果一致，不复制数据库、不缓存整份历史、不另建持久队列或版本库，也不为绑定身份预先计算所有业务视图。
3. **保留下一批待办。** 发布之后观察到的追加合并到下一轮；最多一个同步任务和一个合并待办。只有当前批次确实未完成／凭据失效时才返回待办，已完成批次不等待外部文件静止。普通的来源发现、旧内容修改校验、通知丢失回退继续执行；SHA来源不会因此获得“未检查也知道没变”的能力。
4. **让查询实际读到完成版本。** 同步交接时，已等待的读取请求获得一次消费完成版本的机会；优先复用执行器已有发布读者及活动请求持有。后续同步可以继续，但请求不能被不断接上的同步挤掉。慢标签、断连和取消及时释放读者，不等待所有浏览器确认、不无限保留历史代数、不延长200ms空闲退出。
5. **区分返回结果与复用缓存。** 后续原始写入不应否定已经取得的一致读取；写入／复用“当前”响应缓存仍遵守现有来源与数据库守卫。禁止简单删除所有`afterRead`检查、把空`usageVersion`当作成功，或用事后最新指纹给旧结果贴标签。只有经过同一版本证明的HTTP、SSE、status完成身份才能相互对应。
6. **页面逐批推进。** 验证原页面能够在下一批仍处理中显示上一批的新值，旧请求不覆盖较新范围或版本。若确实需要改前端，仅调整已有请求合并、完成和忙碌状态；已知待办不能被当作全部同步完毕，不加新徽标／常驻说明。普通刷新计时终点保持原样，连续段另按“正确的新版本已绘制”计数，不用结束spinner伪造进展。

安全边界保持：来源中途截断／改写仍拒绝无效解析；部分来源提交不代表整轮完成；辅助配置、证据、真实价格上下文变化不能借新路径越过原失效规则；外部数据库提交、库替换、执行器重启使相应进程内凭据失效。普通追加保留每来源每轮最多3次尝试。即便后续没有通知／SSE客户端，已知待办仍能自行续办。

若现有读快照及完成凭据不足以证明一致性，先报告具体缺口及最小必要改动，不改成无守卫返回、无限追新或昂贵的数据库副本方案。

### 3. 短测试先过，再做固定保护对照

新增**8场景×Codex／DSH＝16个确定时序用例**。原16个来源恢复用例继续保留；另跑受影响的执行器、缓存、SSE、取消、冷热发布和真实原生专项，不反复跑全套寻找绿色。

| 新场景 | 核心断言 |
|---|---|
| 提交后、发布前继续追加 | N能返回和显示，N+1保留待办；三代连续推进不需要静默窗口 |
| 无来源竞争的持续追加 | 新逻辑不只在`sourceRetries>0`时生效；普通路径同样不追逐无穷未来输入 |
| 查询取得快照后下一轮提交 | 金额、事实、元数据、周期与版本一致；缓存守卫不被绕过 |
| 三标签与重复唤醒 | 共享同步；已等待查询能前进；队列有界，慢标签不会锁住采集 |
| 辅助依赖改变 | 配置、证据、价格／汇率分别注入，保留各自原有失效／快照语义，不混版 |
| 已读来源的截断／等长改写 | 旧证明不被复用，下一轮按既有规则核对，最终与完整解析一致 |
| 外部提交／库替换／进程退出 | 旧内部凭据拒绝复活；重开恢复，部分提交不误发布为完成 |
| 待办、取消与关闭 | 无新通知仍能续办；切换范围取消旧等待，关闭后读者、计时器和子进程释放 |

核心用例以握手推进，预期在分钟量级完成；超时只是失败上限，不靠长时间等待覆盖竞争。旧版本必须先失败，候选必须证明至少三代批次的正确进展。小测试失败不进入大数据保护组。

真实页面固定工作量：

| 部分 | 次数 | 验证内容 |
|---|---:|---|
| 当前／一年／两年×`401faeb`基线／候选 | 6组 | 原页面首次today／all、Codex／DSH／ZCode各1次普通追加、today／week／all切换、服务重开 |
| 两年候选连续段 | **90秒、18条** | 三标签，5秒一次，Codex／DSH交替；停写前至少2个正确完成版本且两个来源均推进 |
| 连续段收尾 | 1次 | 无手工刷新／新提示排空，最终独立数量／费用oracle，再重开一次并观察空闲资源 |

合计**6组、36条追加、7次重开**；不对已知会失败的基线重复跑持续段。两版同起点、同价目与后台检查条件，顺序交错，原堆预算不变。三种布局只保留循环复用所需回滚副本，恢复后立即删除。页测包括真实来源检查／同步／解析，不复用上一卡数字代替本轮配对基线。

90秒依据上一卡单轮同步约16秒、普通刷新约30秒设定，足以观察至少两次推进；并非承诺真实页面全部验收只需90秒。按上一卡耗时，原页面整包预计约30–45分钟，包括数据保护／恢复、独立oracle、各组空闲观察及重开，实际分别记录。三标签启动准备不算进持续输入时长；没有额外小时级浸泡段。

## 统一验收标准

| 项目 | 标准 |
|---|---|
| 复现及一致性 | 旧版精确复现；16个新用例全部通过；原来源恢复等相关回归无新增失败 |
| 持续推进 | 90秒内按时落地18条；最后一次输入前≥2个实际绘制的完成版本，Codex／DSH均有进展；意外HTTP错误0 |
| 刷新语义 | 每次完成覆盖该请求交给同步的输入边界；不返回更早缓存冒充新数据完成，不用空版本或spinner替代数据证明 |
| 排空和最终核对 | 末次输入后≤60秒全部正确显示；不靠手动刷新／重启／新通知；独立金额、数量、会话及重开核对通过 |
| 普通速度R | 27项不同指标，与本轮基线比较：同时慢>10%且增加>100ms才失败；分别列出普通刷新、启动、切换、重开，不合并均值遮盖退化 |
| 工作量 | 无冲突普通追加无额外整轮同步、重复事实或全量投影重建；ZCode保持净增1；不把刷新成本转移到启动／重开 |
| 内存与释放 | 服务树同时RSS及高水位补充≤512MiB；普通段及连续段结束后各观察120秒，≥60秒空闲≤256MiB；默认堆与200ms退出不变 |
| 成本证据 | CPU／逻辑I/O／WAL及观察者开销单列；缺采保留“未完成”，不补0；只读oracle在执行器退休后进入，避免人为留住WAL |
| 清理与交付 | 成功或失败都恢复测试来源／状态、删除无用大副本，核对自有进程退出；补丁、失败证据与对照表本地提交后停止 |

当前版已有的4项相对历史退化仍保留记录，本卡不追优，但也不能借冻结范围豁免新退化。一次配对不声明p95或长期稳定性。真实原生证明跑现有小型专项，不另开原生性能矩阵。

**失败时的收尾顺序作一项改进：** 若只是不满足持续推进的时间标准，先记录失败、停止注入；在数据和资源仍安全时，利用已产生的数据完成有上限的排空、独立oracle和额外重开，再恢复现场。避免因为一个时序断言提前抛出而再次丢掉收尾证据。若出现真实数据错误、资源超限或进程失控，停止剩余负载，保留最小诊断证据并恢复。任何情况都不清除原失败，也不为了结果好看补样；只有必要修复或确认的实验缺陷才重跑受影响检查。不会自动升级为两小时／八小时测试。

## 收尾脚本修正（2026-11-11）

原六组最后一组已显示完整新值，但其他标签还有正常查询，驱动误把“每条输入已在某个标签绘制”当作所有标签收尾，随后触发10秒执行器退出上限，未进入独立oracle及额外重开。原失败及27项速度保留，生产候选冻结不变。

只补受影响的两年候选组：首个完整新值的60秒门照常记录；之后被动观察每个标签的完整输入、非空版本、可见总量及忙碌状态，三个标签均结束后再关闭额外标签、等待执行器正常退休、运行oracle及额外重开。此安全收尾仍受末次输入后300秒上限约束，不能通过提前关标签、发新提示、手工刷新或重启制造收敛。补充结果单列，不替换原六组速度或隐藏原脚本失败；工具新增两项短测试。
