B 专项 33/33、历史相关 442 通过／14 跳过、类型与 lint 通过；完整回归 3,227 项中 3,156 通过、69 跳过，仅余两项已有皮肤 UI 失败。显式切换要求全程文件租约及独立 DELETE 模式归档，普通验证回退不变。当前分段证据显示 SHA 明显下降、汇总与部分来源处理变慢，但具体因果尚未证明；保留全部失败，不自动扩大矩阵或开始下一卡。下文为原冻结计划与门槛。

## 1. 为什么先做这个

依据[上一卡同轮实测](../../experiments/architecture-20261101/ARCHIVE-VERIFICATION-REUSE-REPORT.md)：

| 已有事实 | 下一步含义 |
| --- | --- |
| 普通追加已不复制冷事实，已验包的重复语义扫描已归零 | 继续改业务汇总不是这张卡的优先项 |
| 两年一次追加仍读取归档 57,522,520,064 B，SHA 约 22 秒 | 全字节检查仍是明确的大头 |
| 重开有两个独立页面操作，读取 115,045,040,128 B，SHA 约 44.6 秒 | 缩小归档同时改善刷新和重开，无须扩大验证复用范围 |
| 八包共 28,761,260,032 B，其中 freelist 空闲页 16,572,485,632 B（57.6209%） | 目前正在反复检查大量已经没有有效记录的空间 |
| 创建归档的现有路径为复制主库、删除区间外事件、再备份 | 要同时解决已有包和以后新建包的膨胀 |

仅扣除 freelist 的纸面估计约为 12.19 GB，**不是压实实测大小**。若实际接近这个比例、单位字节成本相近，追加可少约 13 秒，重开可少约 26 秒；其他来源解析、查询和费用回放不会因此消失。先用一个真实包验证，不先跑新的大矩阵。

## 2. 阶段门 A：只做一份真实包

从既有两年八包中选一份完整归档，在私有副本上构建一次新文件。旧包、新包各做一次相同口径的完整验证／SHA计时，记录文件大小、CPU、读写、内存和临时磁盘。

选择**保留行身份的顺序重建**，沿用项目已有的 schema、表复制、证据与发布工具：

- 保留明确主键、业务所依赖的隐式 rowid、AUTOINCREMENT 状态、同时间戳顺序及全部逻辑表内容；WITHOUT ROWID 表按其主键处理。
- 在目标临时库中受控装载行，恢复索引、触发器及 schema 元信息，避免装载触发器再次修改事实或派生状态；结束后完整检查。
- 新库逐表对拍，额外比较额度分类需要的 rowid（包括负值、间隙及同时间戳反例）、事件顺序、去重和金额。不能只比较总 token／总行数。
- 新文件验证、落盘和完整标记完成之前，不生成可消费的发布结果；中断留下的候选不可被读取。

不能直接执行一条裸 `VACUUM`：`quota_usage_sources` 没有 INTEGER PRIMARY KEY，但额度判定使用其 rowid；[SQLite 官方说明](https://sqlite.org/lang_vacuum.html)明确指出这类表的 rowid 可能在 VACUUM 中改变。现有 `UsageHistoryQuery` 已显式保留该身份，应复用这项契约。

**继续条件：** 所有语义精确一致；新包 ≤旧包的 60%；同口径完整 SHA 耗时 ≤旧包的 65%；维护进程树 ≤512 MiB；不存在未解释的全量内存载体。只做一次旧／新配对，不能宣称稳定分位数。

任一条件不满足，停在 A 报告实际结果，不批量压实另外十二包、不开始迁移框架或完整页面矩阵。

## 3. 阶段门 B：已有归档迁移和后续新包闭环

### B1. 新文件与旧文件并存

压实是一次**显式维护**，不挂到普通刷新或服务启动。先在原位置之外产生新文件和新 manifest；沿用现有安全发布流程，完整持久化成功后才能切换引用。逐包处理，默认一个维护执行单元，不并发压实八包。

旧包内容及路径保持可回滚。新 manifest 保留原价格、证据和归档范围快照，重新计算真实字节摘要；不能拿当前价格替换历史快照。

### B2. 在原有主库事务内切换全部引用

当前 `segment_id` 就是数据库 SHA，压实一定生成新 ID。记录并校验旧→新等价映射，仍保留 `segment_id == database_sha256` 的现有契约，不另造稳定逻辑 ID 层。

提交前核对当前主库版本及全部被替换归档身份。一个事务更新登记、事件授权、修订中引用的 ID／摘要和来源关联；发布对应归档变更版本。读者只见完整旧集合或完整新集合。文件和主库不能假装由一个跨文件事务覆盖，因此次序是“新文件完整落盘 → 主库事务切换”；旧文件继续存在。

压实期间的普通追加、旧值修订或外部修改不会被维护快照覆盖。切换前版本不匹配则拒绝过期提交，保留旧可用版本；不悄悄丢弃变化，也不无限自动重试。

### B3. 保住已有持久投影及升级后的首次打开

需要处理主库注册表、投影中的归档成员映射／导入记录、输入版本和响应缓存，不能只换文件路径。

优先沿用现有投影维护事务，将已证明等价的包身份重新绑定，保留事件 ID、history_ordinal、业务视图及已有修订；不因为 SHA 换了就再复制全部冷事实。不得只改一个缓存 key 来冒充依赖已经更新。

不能可靠重新绑定时，走既有可恢复的派生重建，**其耗时、写入及磁盘计入这次维护，且不允许把它当成保住重开的成功案例**。只有新版本对应投影已就绪、升级后的首次请求无需再补全量构建，才把维护标记完成。主库与派生库之间出现中断，由现有版本检查拒绝错误组合并恢复。

新字节身份的语义完成记录必须来自新包实际完整验证，不能直接复制旧 SHA 的“已验证”标记。维护完成后的首次打开和后续重开都单列计时。

### B4. 以后新建的归档也不再带入空闲页

把相同构建逻辑接入 `createHistoryArchiveCandidate`，在最终证据／manifest 发布前得到紧凑文件。普通完整备份保持原有语义；本卡不全局改变所有备份行为，不删除其他表来缩小体积。

### B5. 回滚与退出

回滚通过当前主库中的逆映射事务恢复旧包引用，保留维护之后新增的热事实及修订。不能恢复一份旧主库快照并丢掉后来数据。旧包至少保留到回滚验收完成；本卡不自动删除，给出可核对的旧包清单和回收条件。

**B 的八类反例：**

1. 行 ID／同时间戳／精确金额顺序／跨来源去重。
2. 已有冷历史修订、原始来源已删除、多个包及冷热交叠。
3. 构建中断、写入失败、空间不足，未完成文件不发布。
4. manifest 不匹配、同大小篡改、替换文件及旧验证记录。
5. 新包发布后、主库切换前强杀。
6. 主库提交后、派生投影就绪前强杀和重启恢复。
7. 构建期间追加／修订、版本竞争、重复执行，不丢新写入。
8. 切换后再次追加／修订，再执行回滚及旧版读取，数据不倒退。

这些用小夹具和进程故障点完成，不为每种故障再构建一套两年归档。B 未通过，不进入 C。

## 5. 一次性成本和持续成本分开交代

报告同时列“维护耗时／CPU／逻辑读写／临时空间”“升级后首次打开”“普通刷新”“重开”。按实测维护成本与刷新节省计算回本次数，不能把建设费用隐藏成后台任务。

旧包保留时总磁盘占用可能暂时增加。逐包处理只能限制临时工作集，不能承诺零额外空间。A 先实测单包空间高水位，B 据此计算：已完成新包＋当前包临时文件＋回滚映射／必要派生维护空间；空间不足则在发布前停止，不删旧包腾空间。既有两年投影／WAL 约 15.41 GiB 峰值也继续列出，不能只报告压实文件变小。

原资源采样已有 PID 复用归属问题，沿用上一卡修正规则：只计属于本组 runner 的完整进程身份，保留原始和派生记录。新旧采样口径一致，维护进程计入，不提高常驻容量或改 200 ms 空闲退出。

## 6. 修改边界与交付

预期修改归档候选／备份证据共享工具、主库归档登记及修订映射、持久投影维护、已有 CLI 维护入口及 executor 的必要关闭／协调路径；覆盖归档导出、导入、恢复和旧版读取。按调用链最小接入，不新建存储引擎、不增加依赖、不改原生助手证明协议、不加入 UI 常驻说明。

实现前冻结基线与原包，私有副本完成所有验证。相关回归、原页面和资源门完成后，提交本卡文件并用一份表列旧／新／标准／是否达标；停止等反馈。当前不实施、不提交这份计划之外的生产改动，不部署或替换在用历史。

仍未承诺：一年／两年的合成扩展等同真实长期分布、长期尾延迟、跨平台、完整原始重建提速。压实只减少物理字节，不改变完整 SHA 的线性成本；其后仍慢的来源处理／查询另立证据再决定。
