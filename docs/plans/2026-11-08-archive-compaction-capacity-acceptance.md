## 1. 本卡要回答什么

确认 `117ba88` 的归档压实，在一年、两年混合布局下究竟能把刷新和重开降到多少，是否保住一年收益，以及有没有把节省的时间转移到首次启动或升级。生产实现保持冻结，复用已有原始数据、索引种子和十三份压实包。

用户已接受上一卡当前混合布局的五项延迟退化。因此，本卡可以越过原来的当前规模停止条件；**这五项仍标为“未达原标准、用户已接受”，不改写为测量通过，也不自动豁免一年或两年的新失败。** 之前的当前四组页面和一次升级结果直接引用，不重新跑。

参考：[上一卡报告](../../experiments/architecture-20261101/ARCHIVE-COMPACTION-REPORT.md)、[原冻结标准](2026-11-08-archive-compaction.md)、[总路线图](2026-11-02-multi-harness-history-refactor.md)。

## 2. 固定工作量和顺序

旧版为冻结的 `9fae129`，混合布局使用原包；新版为冻结的 `117ba88` 运行时，混合布局使用已完成压实和精确对拍的新包。全热布局两版都不使用归档。

| 执行顺序 | 数据与布局 | 旧版 | 新版 | 本项回答的问题 |
| --- | --- | ---: | ---: | --- |
| 1 | 一年全热 | 1组 | 1组 | 无归档收益时，普通采集、查询和启动是否退化 |
| 2 | 一年四归档＋近期数据 | 1组 | 1组 | 一年刷新、切换、重开是否保住，压实是否有收益 |
| 3 | 一年已有投影升级 | 同一主库上升级前测量 | 维护后首次打开＋再重开 | 升级是否保留已有投影，维护成本是否完整计入 |
| 4 | 两年八归档＋近期数据 | 1组 | 1组 | 两年刷新、重开是否达到下表目标 |
| 5 | 两年已有投影升级 | 同一主库上升级前测量 | 维护后首次打开＋再重开 | 大规模升级是否重新复制或重建冷历史 |

**上限是六组原页面运行＋两次升级闭环，不增加新的原型、数据规模或完整导入。** 各格一次；不是 p95 验收。先完成每对新旧版并分析，再进入下一项；一年验收通过后才进入两年。

六组沿用原序列，每组包括：

1. 启动服务到正确默认首屏，再进入首次 all，首次投影建设包含在内。
2. today、week、自选日期、all 切换，以及重复 all、执行器退出后查询。
3. 六种 harness 各追加一次，等待原页面显示正确新值。
4. 一次 ZCode 旧记录修订，核对修订后的精确结果。
5. 完整停止并重开服务，再到正确 all 页面。

主对照合计 **36次追加、6次旧修订、6次服务重开**；三个新旧版配对各17项延迟指标，共51项比较。旧当前结果另列，不能混进这51项宣称全部新测通过。

每次升级闭环额外包括：旧版建立一次已有投影（setup单列）→旧版首次打开和再重开→显式引用切换及投影维护→新版首次打开和再重开。两次闭环共10次页面启动窗口，其中2次是setup；形成4项升级前后延迟比较。主库保持同一路径和文件身份，投影原地维护，不能拷贝一份预热结果冒充升级。

## 3. 结果、标准和是否达标放在一起

### 延迟标准

统一防退化规则：某项**同时**比同轮旧版慢超过10%，且多超过0.100秒，才判未达标。金额和业务结果没有容差。下表沿用原定标准，不根据新成绩调宽。

| 验收对象 | 操作 | 标准 |
| --- | --- | --- |
| 一年全热／混合 | 每组全部17项操作 | 逐项通过同轮防退化规则；不能用其他操作的收益抵消 |
| 一年混合 | Codex／DSH追加 | 分别≤29.02／42.06秒，且通过同轮防退化 |
| 一年混合 | Claude／WorkBuddy追加 | 分别≤54.84／39.02秒，且通过同轮防退化 |
| 一年混合 | ZCode／OpenCode追加 | 分别≤54.74／39.86秒，且通过同轮防退化 |
| 一年混合 | 旧修订／已有投影重开至all | 分别≤79.86／42.14秒，且通过同轮防退化 |
| 一年混合 | 投影完成后的范围切换 | 各不高于C1对应操作的20%，同时通过同轮防退化 |
| 两年混合 | Codex、DSH、Claude、WorkBuddy追加 | 各≤35秒，并比本次配对旧版更快 |
| 两年混合 | ZCode／OpenCode追加 | 分别≤45／42秒，并通过同轮防退化 |
| 两年混合 | 服务重开至all／旧修订 | 分别≤45／78秒，并通过同轮防退化 |
| 两年混合 | 其余操作，包括首开至首次all | 逐项通过同轮防退化，首次建设不移到计时之外 |
| 一年／两年已有投影升级 | 升级后首次打开、再次重开 | 各与本布局升级前已有投影配对，通过同一防退化规则 |

## 4. 测量方式与一次性成本

- 使用现有Windows机器、原页面和真实来源检查、同步、解析、版本通知。继续采用E:来源的SHA路径；归档维护使用既有文件租约助手，不安装助手或启用系统journal。
- 新旧版串行运行，不并行做完整回归、压实、导入或其他重型实验。沿用相同价格检查条件和业务时钟回放，保留实际状态写入。操作系统缓存状态如实记账，不称OS冷缓存成绩。
- 追加从完整原始记录可读／来源事务提交开始，计到正确新值绘制；不是只计API，也不是spinner消失。子阶段是嵌套时间，不能把SHA和包含它的同步时间重复相加。
- 主矩阵的首次打开包含必要的首次投影建设与验证；已有投影升级另测，不能混用两种启动定义。升级setup、引用切换维护、升级后首开、再重开四笔费用分开列。
- 已完成的十三包不重建。包构建及验证成本引用原回执，明确属于上卡；本卡新增的维护、CPU、逻辑I/O和空间单独记录。只有实测节省为正时才计算简单回本次数，并注明是单样本算术。
- 使用既有资源采样与精确PID／创建时间归属规则，记录主库、投影、候选、WAL和可见临时文件。旧新包并存约51.138GB是已有占用，不能报成本卡新增；历史两年投影／WAL约15.41GiB峰值仍列作准备预算。沿用至少64GiB空闲空间预检，不靠删除旧包腾空间。
- 完整物理临时峰值尚有观测缺口。本卡列明采样覆盖路径和卷空闲量变化，不把目录可见0写成零临时开销，也不把逻辑I/O写成SSD物理I/O。

## 6. 失败与停止规则

1. 预检不符、输入损坏、正确性错误、版本混用、数据丢失、OOM或资源超标，立即停止受影响运行，保存证据，不继续扩大规模。
2. 新的性能门失败，在该新旧配对完成并分析后停止后续大组。先使用本次已有分段轨迹定位，不自动再跑一整套、不用复测替换失败、不把新增失败算入用户此前接受的五项。
3. 运行器错误若发生在页面启动之前，保留无效尝试，修复工具后可继续该尚未形成样本的组；已进入计时的失败必须留在结果中，不能悄悄重置。
4. 没有预授权额外性能组或业务修复。需要新的定位样本或生产改造时，在本卡报告中列清证据和最小后续范围，再停下等反馈。

因此“六组＋两次”是本卡固定完整范围，也是上限；不是出现错误仍必须跑完的配额。用户已接受的旧五项不再触发本卡停止。
