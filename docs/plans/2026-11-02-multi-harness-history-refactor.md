## 一、目标从“跑得快”改为“增长后仍可负担”

多 harness 和不断增长的历史是正常负载。设计应让日常操作的工作量主要由本次变化、受影响分区和返回结果决定；历史事实主要存于磁盘，内存服务于当前工作集。

必须同时达到响应、资源和正确性要求，不能用加大堆、长期保留完整历史对象、减少必要检查、频繁退出执行器或推迟新数据可见性来交换成绩。

区分三种成本：

- **首次导入/完整重建**需要读取真实输入，工作量允许随总输入近似线性增长；重点消除重复扫描和超线性退化。
- **普通刷新**主要处理变化来源中的新增/修订内容及其依赖，不应反复读取全部历史或完整当前长会话。
- **界面查询**读取已提交派生结果；成本随请求范围、边界明细和返回规模增长，不默认物化全历史。任意精确大查询仍可能昂贵，不承诺所有查询恒定时间。

### 容量失败后的决定：先改变计算方式，再继续降低延迟

阶段 A 的 5×/10× 事实已全部提交，随后执行器在默认堆下失败。当时尚未定位首个 OOM，也不能据此断言数据库无法容纳数据；B1 随后在隔离副本复现额度载体的故障并改造。采用**以磁盘事实和持久业务视图为中心、有界处理的查询通路**，不以移除第一份数组后不崩溃作为完成条件；本轮增长结果见 B1 报告。

这延续本计划的一个候选，不再增加原型路线；变化在于把容量变成 B1 的先决条件。即使精确定位发现只需很小改动即可避开本次 OOM，后续完整查询、会话增长和年份增长仍须过关。阶段 A 剩余增长轴作为 B1/C 的定向验证继续完成，不再以补齐所有旧基线为前提延迟容量改造。

| 环节 | 当前已确认的增长风险 | 目标职责 |
| --- | --- | --- |
| 额度 | `quotaObservationsFromDatabase` 整表转对象，消费者再筛选/排序 | 按窗口与请求时刻查询候选；完整窗口历史留在磁盘，保留过期、冲突和冻结时刻语义 |
| 历史纪录 | `buildRecordChampions` 虽逐行读取，仍在各周期保留会话/模型集合，并重复遍历事件 | 持久基础统计和精确成员关系；只读取必要周期结果，修订可撤回，组合来源重新比较 |
| 冷历史 | 多分片、修订覆盖等路径合并全量事件再汇总 | 校验后按范围读取、分批合并，工作集不由分片总事件数决定 |
| 明细与传输 | 分组会话 ID 等结果本身可能增长，序列化还可能产生副本 | 总数与成员明细分开获取；大结果分页或流式传递，保持精确统计和既有可访问内容 |
| 重建与发布 | 事实导入完成不等于业务结果可用；失败后缺少可直接使用的摘要 | 批次推进事实/派生进度，完成并核验候选结果后发布；失败可从已提交边界恢复 |

这里的“分批”同时约束**输入、中间结果和输出**。把读取改成迭代器、却继续向一个无限增长的 Map/Set 累加，不满足要求。会话去重关系、额度窗口历史、排序中间结果需要索引化磁盘结构；按字节预算处理批次，单个高流量日也必须可分批。成员关系可随历史在磁盘增长，进程不同时持有全部成员。

复用现有 `usage_rollup_sessions`、dirty days、事实表及摘要机制，优先扩展缺失的统计。计价仍按请求的完整语义计算，再保存可精确合并的贡献；不预生成所有筛选组合，不复制完整事件作为另一套内存数据库。首轮只增加实际页面所需的持久结构。

额度的落地约束已核查 `selectQuotaWindows`、`completedQuotaWindows` 及上一窗口/纪录消费者：限额桶选择依赖全历史的有效观测数和最新时刻，不能先按当前时间截断；窗口推断保留冲突、两分钟抖动容差和晚到旧快照判断。桶统计与窗口支撑信息可以在磁盘维护，但把每条观测缩成一个 `anchor` 再全部返回，仍然没有容量边界。当前窗口、上一窗口、纪录分别取得所需结果；旧时刻查询要能按该时刻重建，修订要能撤回。原始报告/备份的完整观测字段继续保留，不能因为看板不使用某字段便删除其对外契约；`official_quota_observations` 的整块 JSON 也纳入大小与迁移检查。

SQLite 的排序/去重中间结果**可以**使用临时磁盘结构，但不能假定换成 SQL 就自然有界：须核对实际构建参数、执行计划、缓存和临时文件峰值。[SQLite 临时文件文档](https://sqlite.org/tempfiles.html)说明临时结构的位置还受编译及运行设置影响。持续写入期间也不能靠一个贯穿重建的长读事务来保留旧视图；长读可能阻碍 WAL 回收，且多个 WAL 数据库不天然整体原子提交，见 [SQLite WAL 文档](https://sqlite.org/wal.html)。沿用发布版本核验，选择可恢复的短事务及候选视图，不把内存问题转移成无界 WAL。

**完整重建与日常服务采用不同的执行方式，使用同一份事实和业务规则：**

```text
首次导入：真实来源 → 有界解析/暂存 → 事实批次 → 持久业务统计 → 核验发布
日常追加：变化来源及依赖 → 更新事实与受影响统计 → 核验发布
页面查询：一个已发布版本 → 小型汇总或一页明细 → 浏览器
```

第一次处理几十 GB 原始内容仍有读取和解析成本；允许耗时随输入增长，但不能因为历史装不进 JS 堆就失败。已有事实时，业务视图重建不再要求重新解析所有原始日志。正常重启、刷新和切换不再触发这种重建。候选构建进度与发布状态分开，旧版本可读不计作新数据完成；空库首次导入不能用部分历史冒充完整首屏。

**一年、两年的目标必须直接测试。** 已有 10× 只是在同一 90 天、同一批文件/会话中增加密度，不等同于两年。B1 增加 365/730 天及独立会话增长的派生构建诊断，明确这些仅覆盖事实库之后；C 再覆盖真实格式的长期来源发现、导入及多冷分片。输入规模按冻结的来源画像生成并记录，不能仅把日期拉长而声称证明了两年容量。

## 二、已有证据及尚未证明的部分

已测到的主要浪费：

1. 会话累计查询 1,493 次耗时 29.6 秒；补复合索引后约 17 ms，同探针完整重建 82.6→52.0 秒，事实一致。
2. today 页面中的历史纪录计算仍遍历完整历史；单次约 1.25 秒。原实现已有 rollup 和持久摘要，后续优先扩展这些机制。
3. 原型启动仍跨进程搬运约 142 MB 事件并重建业务视图；当次服务树 RSS 样本超过 1 GiB，不能直接搬入正式路径。
4. `SourceBusinessViews` 虽按来源重算，仍将全量事件、成员集合和多个范围的贡献保存在进程内；这证明了部分合并语义，没有证明容量扩展性。

本次代码复核补充三个实施约束：

- `public/app.js` 当前每 **60 秒**自动检查一次；“记录落地→新值显示 ≤1 秒”必须包含及时唤醒与页面通知，不能只测请求发出后的耗时。
- `UsageStore.syncRound` 已有 `changedSessions/earlierFileChanged` 级联，解析器通过 `previousCumulativeForSession` 读取跨文件累计基线；“只处理变化文件”会漏掉依赖它的后续文件。
- `UsageSummaryCache.publish` 当前遇到任何冷分片就停止发布缓存，以保留冷包核验。增加持久视图不能直接取消这道保护；必须连同冷历史的读取和验证一起设计。

当前保留索引约 16 万条事件；可从现存原始来源重建的样本约 14.6 万条事件、约 4 GB 输入。[历史量基线](../../experiments/architecture-20261101/GROWTH-BASELINE-REPORT.md)记录 B1 前实现的容量失败；本轮 B1 的默认堆下 1×/5×/10× 各三次已全部成功。它覆盖同一 90 天内的密度增长，不能代替长期来源、活动实例或冷分片的增长曲线。

另一个必须覆盖的路径是冷历史：`UsageStore.trySqlHistoryDashboard` 的 SQL 快速路径当前仅适用于 all、单个获授权分片、无修订覆盖等条件。其他情况的 `dashboardHistory` 会请求 `completeHistory` 并转换全部事件。上轮真实库 `archive_segments=0`，其成绩不能外推到多个冷分片或热冷混合历史。

## 三、目标数据通路

```text
六类来源适配器
  → 发现变化、读取增量或安全替换
  → 持久事实 + 采集进度 + 受影响分区
  → 更新有确切依赖的派生结果
  → 原子发布一致版本
  → 小型查询结果及版本通知
  → 浏览器显示该版本
```

复用现有事实库、来源解析、rollup、事务及发布机制。暂以 Node + SQLite 实现这一条正式候选；语言与存储保持可重新评估，不把当前结论写成永久限制。

### 1. 保留不同 harness 的语义，统一后面的提交和查询

六个现有适配器分别明确来源身份、格式版本、增量依据、解析状态、修订/删除处理和恢复方法。

- 普通日志按已经验证的完整记录推进；持久进度需要同时保存累计解释状态，不能只保存字节 offset。
- 压缩来源按其实际帧/版本语义处理；完整帧校验和现有坏帧行为保留，不能简单对压缩文件 seek 后当成新日志。
- SQLite 来源优先利用可证明的记录标识/修订能力和一致读快照；仅有 MAX(id) 不足以检测旧行更新或删除。
- 不具备可靠增量信息时，保留受影响来源的完整处理回退，并计入该来源的尾延迟。不能把所有 harness 都假定为只追加。
- 先在 Codex、DSH 完成原始输入到页面的纵向切片，再接入其余四来源的共同提交/派生路径；阶段验收覆盖六类来源。

文件通知用于及时唤醒，持久进度与现有核验仍负责正确性；漏通知、替换、截断、重复输入、来源暂时失联均要验证。没有可信变更依据时，必要检查本身的扫描成本不能被口头消除或从刷新计时中剔除。

核对 `/api/status`、加载前、同步及发布后的重复发现/指纹工作；同一轮可证明仍有效的来源清单与观测应复用，提交前防止输入变化的复核保留。每轮报告扫描次数与字节，减少重复工作不能变成假定文件始终不变。

增量的单位是**变更及其实际依赖**。旧文件修订可能改变同一会话后续文件的累计基线，需失效相应解析检查点并重算依赖链，直到能证明后续解释不再变化；不能只撤回旧文件的汇总。身份沿用现有 home/session 语义，并覆盖文件改名、普通/压缩表示切换。依赖链重算的范围和成本单列，不能把它隐藏成普通追加。

### 2. 按可修订分区保存贡献，避免全局失效

从现有 dirty days/rollup 扩展所需分区。历史追加、迟到事件、来源替换、价格或证据变化，都要能定位受影响的来源、日期、模型等依赖；变化前贡献需要能撤回，不能只支持数值累加。

不预计算全部来源组合、全部自定义范围和所有维度笛卡尔积。固定少量可复用的基础汇总；查询时合并必要分区，范围边缘读取索引化明细，特别结果使用有字节预算的缓存。

数据修订、价格/汇率版本、证据版本、时区和派生算法版本应分清依赖。价格变化不需要重新解析原始日志，但可能需要重新计算全部受影响的计价分区；这种真实工作照常计量，不能使用旧价格结果冒充完成。

为实际页面字段列出一张最小依赖表：权威输入、持久基础值、失效条件和必要回退。普通追加优先直接更新可精确增减的计数与贡献；其余只重算必要分区。不能把“每次扫全历史”改成“每次重扫整个高流量日”就视为增量完成。复用既有表与版本字段，不为这张表新建通用依赖框架。

时间本身也是输入：午夜、周/月边界、额度窗口到期以及未来时间记录进入范围时，即使来源未变，视图也必须正确推进。沿用 `refreshSummaryClock` 和现有有效期机制，分别处理可直接重算的时钟字段与已到期的统计结果。

### 3. 精确处理无法直接相加的字段

- token 等满足条件的统计可合并；跨天、跨文件、跨来源的去重会话数不能直接相加，应使用保留原有身份语义的成员关系或等价精确方法。
- 历史纪录保留日/周/月等必要基础值，再按选定来源组合比较。不能只保存各 harness 的最高纪录：合并后的最高日可能不是其中任何一个来源的最高日。旧历史修订还可能让原纪录下降，需要能重新选取。
- 金额不能一律“先加 token 再套价格”。请求级分档、缓存写入、服务层级、时间段、未知字段及现有最低费率语义要保留；只有证明足够表达原计价语义的数据才可合并。
- 精确统计不改成抽样或近似去重；遗漏明细、损坏来源和缺失冷包不能返回成功的残缺统计。

### 4. 日常读取只加载需要的结果

常用看板、历史纪录及多周期结果持久保存，重启后直接读取。明细分页/流式读取，不在页面或网关启动时装载整个事件载体；执行器生命周期不再决定派生结果能否复用。

热历史和已封存历史遵守同一查询口径，多个冷分片、修订覆盖、今日/自定义范围必须有受范围约束的读取路径。保留现有 authority、校验和历史保留契约；本轮不通过降低冷包校验频率取得成绩。

每次发布必须绑定同一事实和派生版本，复用事务或等效的不可分割发布边界。对外可读旧版本不等于新数据刷新成功；新增数据只有校验、提交、派生和页面显示全部完成才停止计时。实现机制不转化成常驻 UI 说明或额外警告框。

原子性针对一次可确认的发布，不要求把六来源整轮读取、解压、计价全塞进一个长事务。先形成有界批次，重验输入后提交；事实、采集进度及可恢复的派生任务不可脱节。小更新优先在同一短事务完成；确实需要跨事务重算时，候选视图按版本隔离，完成后才切换可见版本。现有摘要是独立 SQLite 文件，不能假设两库提交天然原子；保留发布版本核验，缓存失败可由已提交事实重建。

不同来源可以独立推进，但相互依赖的会话修订必须形成一致发布。一次刷新明确记录已核验到的来源边界，持续写入不要求等到全世界静止；该边界前应纳入的数据必须全部正确可见才算完成。来源失败沿用现有错误语义，不能用其他来源成功冒充整轮成功。summary、metadata、quota、periodComparison 及分页结果绑定同一发布和请求时刻；复用已有冻结快照与页面请求序号，防止晚到响应覆盖新选择。

### 5. 资源由工作集决定

批次、解压和数据库遍历采用有界流及背压；共享少量执行器，以待处理工作和源间公平性调度，避免每个 harness 各持有完整历史副本。单条超大合法记录需要专门处理，不能为了守住内存数字把它丢掉。

只缓存需要复用的小型结果，限制实际字节而非仅限制缓存条目数。将冷启动、运行中、后台重算和整理的 CPU、读写量、内存一起计入资源账本，不把代价移到测试结束之后。

长导入、重计价和整理按有界批次让出执行机会；一个繁忙来源不能让其他来源或交互查询无限排队。优先复用现有执行器，不预设增加线程池；是否需要独立读执行器由并发延迟与总资源实测决定。记录最老待发布数据的年龄及负载停止后的追赶时间，避免低内存仅仅意味着队列越积越长。

### 6. 把及时发现与页面更新作为完整链路交付

自动刷新开启时，来源通知唤醒服务核验与采集，提交后只向页面通知可读版本，页面再取小型结果；先采用单向版本通知所需的最小机制，不另建消息总线。保留必要全检与定期补查，覆盖漏通知、重连、睡眠恢复和新目录发现。通知可合并，事实不能遗漏；多标签页共享服务采集，不能各自触发全量扫描。

自动刷新关闭时保留现有冻结语义。前台正常通知路径、漏通知后的补查、后台标签页恢复分别计时；1 秒目标适用于前台自动刷新开启的普通追加，不能主动调用刷新 API 后才开始计时。没有可靠通知能力的来源若达不到目标，仍记为该来源未达标；不能偷偷改成高频全盘扫描来过关。

## 四、三个交付阶段

### 阶段 A：建立扩展基线并落地已验证的查询改进

阶段 A 历史检查点：**索引、DSH 单遍导入及历史密度的完整重建基线子项完成；B1 前实现的 5×/10× 容量未通过**。索引接入、旧库无损补索引及写成本见[索引验证报告](../../experiments/architecture-20261101/INDEX-STAGE-REPORT.md)；DSH三对完整重建、字段哈希与资源结果见[单遍导入验证报告](../../experiments/architecture-20261101/DSH-STAGE-REPORT.md)；1×/5×/10×的旧版耗时、CPU、内存、I/O和磁盘见[历史量基线报告](../../experiments/architecture-20261101/GROWTH-BASELINE-REPORT.md)。当时按要求停止，未进入 B，也未将阶段 A 整体标为完成；用户随后授权本次 B1，当前状态以本文顶部及 B1 报告为准。

本轮正式矩阵每档三次，固定六实例、1,968文件、1,729会话与90天，使用真实物理目录检查和读取。1×首屏中位40.573秒；5×/10×各三次均在全部事实导入后触发执行器OOM，失败响应中位158.933/311.095秒，不能当作完成首屏耗时。九次事实的计数/总量预期及SQLite完整性检查通过，原始输入和正式源码哈希未变。没有提高现有堆配置；失败时较低的RSS不代表资源目标达标。

B1 随后用隔离事实副本定向复现并定位了额度载体的 OOM 路径；该诊断不冒充旧九轮缺失的故障栈。改造和验收见下文及 [B1 报告](../../experiments/architecture-20261101/B1-REPORT.md)。独立会话数、年份跨度诊断在 B1 补充，文件数、活动实例数与冷历史仍按后续 B/C 继续完成。

完整重建优化：沿[上游对照与重建再分析](../../experiments/architecture-20261101/UPSTREAM-COMPARISON.md)定位的重复工作，已实施保留现有语义、使用有界暂存的 DSH 单遍导入。此前三组配对均更快，中位58.506→51.203秒，CPU和执行器峰值RSS均下降；该真实样本未触发暂存落盘，超预算路径由夹具覆盖。本次密度基线暴露了导入后的容量失败，后续先定位这一工作集，再按证据安排采集与业务视图改造；后续B/C验收不因此跳过。两批目录I/O和测量挂钩不同，不直接用绝对秒数宣布新收益。

交付一个可单独审查和接入的复合索引迁移，包含旧库迁移耗时、索引体积、写放大、回退及全部采集/业务回归；保持当前六来源与历史保留行为。核对现有 schema 约定后选择最小迁移，不将此项与后续业务视图改造捆绑。

同时建立后续统一使用的增长基准：真实数据用于绝对校准；同一生成规则构造合成 1×、5×、10×，用于增长曲线，并核对合成 1× 与真实数据的差异。固定源码、输入、harness 组合、记录可见时点、后台设置和统计契约；构造新事件/会话身份，避免复制数据后被去重。初始索引和原始来源路径一致，源目录/stat 等实际 I/O 不能由内存目录回放冒充。

主规模轴为历史事件及其原始字节，固定活动来源、本次增量、查询输出规模和文件数；另做文件数增长与长期日期跨度增长的单变量诊断，分别暴露发现成本和分区合并成本。harness **种类**与实际 home/目录/数据库实例数分开统计。固定文件数无法由某格式自然构造时，明确标注伴随变化，使用定向样本隔离，不宣称是纯历史轴。生成清单记录事件、会话、日期、文件、冷分片、实例数及字节量；真实语义夹具另保留跨文件会话和重复输入，不能通过换 ID 消除这些难点。

出口：确认索引收益属于哪些场景，并给出历史量、文件数、活动来源数分别增长时，时间、内存、CPU、读写量的基线。后续停止继续微调已消除的累计查询。

同时核查冷历史读取与完整性验证的实际成本；如果某项必要保证要求访问全部冷包，其下界必须先说明，不能预设所有查询都能达到常数延迟。诊断工具的 SQL 冷历史快速路径探针已对齐真实方法名；此前真实库无冷分片，该处未参与上轮成绩。

本阶段只建立可复用数据集、指标采集及少量诊断样本，不提前执行阶段 C 的完整重复矩阵和长测，也不以少量样本宣布 p95 达标。先确认 10× 数据集及迁移临时空间是否可容纳；固定历史输入只生成一次并只读复用，活动输入与数据库状态逐轮隔离/恢复，避免每轮复制几十 GB。保存未改动正式版和仅索引版作为后续对照，四原型不再每轮重跑。

### 阶段 B：完成一个可复用历史的正式候选

仍是同一个候选，按以下三个交付点依次验收，避免把采集、查询和恢复一次性替换：

| 顺序 | 交付内容 | 进入下一项前的证据 |
| --- | --- | --- |
| B1 | 以现有采集结果为输入，改为有界的热历史查询与持久业务视图，覆盖额度、纪录及多周期统计，落实可恢复构建与发布边界 | 同一 1×/5×/10× 完整重建均成功，默认堆不提高；新增会话/年份诊断通过；进程重启不默认扫描完整热历史；价格、时间边界、修订下降与会话去重正确 |
| B2 | 接入 Codex/DSH 的来源进度、可撤回贡献、依赖链修订，打通来源唤醒→采集→提交→原页面通知 | 真正追加与完整替换对拍；长会话追加不重复扫描整个文件；漏通知可恢复；采集中切换与终止重启通过；压缩来源按实际能力如实回退 |

每项都在隔离副本做语义对拍、并发读写、故障恢复和 1×/10× 小样本增长诊断；失败先修正该项，不等到 C 才发现架构问题。B1 的热历史成果不代表冷历史目标已完成。

**以下为已完成的 B1 实施与验证记录；当前授权范围是 B2：**

本轮已用 5× 隔离副本复现额度载体在约 200 MiB JS 堆附近的 OOM，随后实施 SQL 额度窗口、持久纪录与精确成员、仓库 rollup、时间线会话落盘和索引化额度来源分类。九次候选完整重建及三次旧版对照全部通过，真实留存库十范围的 63,752 个数字字段精确相同；五组会话/年份派生诊断及进程终止续建通过。最后补齐冷 SQL 视图的 rowid 兼容性回归，25 项相关测试通过，完整回归 2,575 项保留两项已在 B1 前代码复现的 UI 失败。六张 pinned worker 卡已逐卡验收并关闭。

实际剩余项：10× 首次摘要 miss 重启约 16.1 秒，大范围/跨时区查询仍为秒级；1× 逻辑读写增加约 25.8%/34.8%，两批计时存在波动；官方额度/证据 JSON 及冷分片增长尚未覆盖。因此本轮只将容量门标为通过，不把重启和查询出口全部标绿，也不自动进入 B2。轻量定位证据与旧完整基准分开保留，不能称为原始九轮故障栈证明。

1. **定位与数据契约。** 复用失败后已完整导入的隔离事实副本，用轻量函数边界/分配诊断定位峰值，记录每个消费者保留了哪些对象。固定额度、纪录、计价、去重、时间依赖与发布版本的结果契约；重型定位不混入正式性能结果。
2. **替换查询与派生构建通路。** 按定位顺序去掉全历史常驻载体，将必要成员/窗口/周期统计落到可修订的磁盘结构，以有界批次构建并记录进度。同步调整全部消费者、序列化与测试；保留现有六来源采集，B2 再改来源级增量。小数据旧算法及独立手算夹具作对照，不能把会 OOM 的全量回退留作大数据正常路径。
3. **容量及可靠性验收。** 原输入、原页面、原默认堆重跑 1×/5×/10× 各三次，共九次完整重建；增加固定总事件量下 1×/5×/10× 独立会话数，以及按来源画像构造的 365/730 天派生构建诊断，各至少一次。后者单独报告，不冒充端到端年份验收。核对结果、重启复用、中断续建与修订；输出 CPU、逻辑 I/O、服务树内存、派生库/临时文件/WAL 体积，再停止等待反馈。

B1 不仅要求九次不崩溃：同一默认堆下，完整重建到正确首屏仍须接受服务树活动峰值 512 MiB 的既定目标；不允许堆外 Buffer、SQLite 缓存或新增进程隐藏内存。完整重建按解码字节和记录数分别报告单位 CPU/I/O 与耗时，新增持久结果的空间和维护成本必须公开；1× 若出现超过 10% 的同口径中位耗时/CPU 回退，先复核归因，不能默认为可接受。5×/10× 的旧结果是失败，不能据此计算“成功耗时提升百分比”。成功且有界是 B1 的容量门，长期响应目标仍由 B2/C 验收。

本轮元数据审计另发现：1×/10× 的官方额度观察均只有一条、289 字节，密度矩阵未放大 `official_quota_observations`、`codex-quota.json` 与来源证据 JSON 的整块读取。它们继续列在接入前容量清单；来源级处理在 B2/B3 完成时须连同对应查询消费一起验证，不能由本轮事件密度或百万分类点专项代为证明。B1 的一年/两年诊断仅从事实库开始，也不能取代 C 的真实来源长期验收。

复用当前 SQLite rollup 与摘要设施，不搬入四原型的全量内存结构或旧库→新库桥接链路。常用范围及多个冷分片查询不再默认物化完整历史。保留现有精确算法作为结果对照和受控回退，同时为累计、去重、阶梯价格、纪录并列/下降准备可手工核算的小夹具，避免新旧代码共享错误。回退触发及成本有可核查记录，频繁回退视为性能未达标。

主要接点为 `src/usage-store.js`、`usage-rollups.js`、`usage-summary-cache.js`、`usage-executor.js`、六来源适配器、`server.js` 及必要的页面版本通知。实施前核对现有接点和迁移编号；不同时扩展无关设置、皮肤或客户端形态。

出口：六来源完整追加/修订链路、原业务结果对拍、重启直接读取持久派生结果、读取字节和处理分区能够解释。

迁移从既有事实与冷包构建候选派生结果，不能从当前原始文件重建后替换历史。候选核对完成前不破坏旧读路径；保留旧代码能读取的权威事实，明确每次 schema 变化的兼容/恢复方法。测量中断续建、峰值磁盘占用和迁移期间查询，重建派生结果不能要求再次导入已消失的原始来源。

### 阶段 C：用增长曲线和恢复结果决定是否接入

主矩阵为 **3 个历史规模 × 4 类场景，共 12 组**：无变化完整冷启动、单个活动来源追加、六来源同时更新、原页面范围切换。12 组是每个实现的场景数；未改动正式版与最终候选同口径各跑一套，索引版仅在需要归因的场景复测。单来源场景对六类来源轮换，逐来源报告；常用范围和来源切换按预先固定的序列执行，首次与重复访问不混报。

追加按独立于完成时间的节奏注入，不能“等上次完成才发下一条”掩盖排队；分别测日常节奏、六来源突发以及追赶过程中的切换。每个被比较的追加/切换类别至少 100 次尝试，跨至少三个独立服务进程；冷启动每个规模/实现至少 20 次。报告样本数、p50/p95/max及失败/超时数，冷启动 p95 标为小样本观测，接近阈值时按预先固定的规则补样。失败和超时保留在原分母中，超时计为超过阈值，结果错误或崩溃直接使该组失败；不能用重跑替换失败样本或将六来源平均掩盖单来源饥饿。环境异常的排除理由及原记录一并保留。

计时用单调时钟，关联同一输入批次、发布版本和页面请求。追加从完整记录可读/来源事务提交开始，覆盖可见动作本身的测量不确定性；冷启动从启动服务前开始，Chromium 预先启动、每轮新 context，并记录 OS 缓存条件，不声称已经清空系统缓存。页面需显示独立预期结果，不能只比较页面与本轮 API 的 total token：还要核对本次受影响的金额、会话、纪录、额度和范围，覆盖 total 不变的修订。沿用精确结果可见后两帧的观察口径，不能把通知收到或 spinner 消失当完成。每组固定超时、后台任务和输入种子，交错运行基线/候选及规模顺序，记录机器并行负载；轻量计时与重型诊断分开。

另外定向覆盖：停机积压后的启动、首次导入/重建、同等记录量下的多小文件/少量长文件、一个持续变长的活动会话、旧行修改/删除、迟到数据、来源丢失保留、价格/证据修订、跨时区边界和超大记录。冷历史至少覆盖无分片、单分片/all、单分片/today或自定义、多分片、修订覆盖或热冷混合、缺包失败，并记录实际查询路径与核验字节。改变一个变量时其他条件保持一致；非每个变量都盲目做笛卡尔积。

在事务前、事务中、提交后发布前、派生构建中注入终止，验证已确认事实不丢失、重放不重复、游标不超前、结果不混版。数据迁移保留当前原始来源已消失的历史事实。

这些故障在 B 的每个交付点就做，C 只做完整回归；另覆盖磁盘写满/写入失败和数据库暂时占用，验证旧发布可读、失败不冒充成功、恢复后可继续。并发采集期间反复读看板与冻结快照，核对跨字段一致性和现有保留契约。

先通过小样本与语义门槛，再做一小时混合负载诊断、最终八小时长测，覆盖追加、范围切换、价格变化、后台整理、重启和恢复。服务树峰值需持续采样，不能以活动结束后的一次 RSS 代替；短命执行器的 CPU/峰值也要计入。分别报告服务树和浏览器，并观测系统文件缓存/硬缺页压力；同一会话的多页面不应成倍放大采集量。报告每批输入对应的读取/写入字节、重解析字节、重算分区、最长写锁、WAL及数据库/派生表体积。

空闲资源只在队列清空、必要整理完成后取稳定窗口；长测结束继续计入追赶和维护成本，报告最老待发布年龄、排空时间及停止输入后 WAL/磁盘能否收敛。尾延迟、资源和后台债务同时可接受后才进入正式接入；发布/切换仍是独立步骤。

出口：一个通过或未通过的明确结论。若仍是解析 CPU 主导，再为已定位的一段做原生实现对照；若受存储查询/写放大主导，再评价数据库变化。现有四原型只能提供各自已测边界内的辅助证据。

## 五、联合验收目标

以下是下一阶段的工程目标，**尚未测得**，不能写成性能承诺：

- 已有发布状态且来源无变化的完整进程冷启动：目标不超过 2 秒；包含必要来源检查，不包含启动浏览器。它不等于操作系统冷缓存；服务停机期间已有增量待追赶的启动、首次导入和 OS 冷缓存诊断另列，不能只展示最好的一种启动。
- 既有索引的常用范围、来源组合切换：p95 不超过 200 ms；首次未访问范围与重复访问分开统计，空闲和日常采集并行时都验收。重建/重计价突发期间的延迟与恢复另报。
- 普通小追加从完整可解析记录落地到正确新值显示：p95 不超过 1 秒，适用于前台页面自动刷新开启，包含发现、校验、通知、提交与绘制；异常修订/全检、通知丢失及页面恢复另列，不能混进平均数。各来源的“普通”输入大小/记录数在 A 冻结，不能测完后再改分类。
